# F2-A. OCPP-aware Static Analysis 상세 개념설계 초안

## 0. 문서 목적과 적용 범위

본 문서는 ChargeGuard-HVVD 시스템의 핵심 분석 계층 중 하나인 **F2-A. OCPP-aware Static Analysis**의 상세 개념설계를 정의한다.

ChargeGuard-HVVD는 전기차 충전 인프라 소스코드에서 OCPP 프로토콜 맥락과 코드 정적 분석 evidence를 결합하여 취약 후보를 식별하고, 이를 evidence-aware HVVD로 생성하는 분석 프레임워크이다.

전체 기준 구조는 다음과 같다.

```
F1. OCPP-centric Knowledge Layer
  ↓
F2. Hybrid Source Code Analysis
  ├─ F2-0. Common Code Fact Layer
  ├─ F2-A. OCPP-aware Static Analysis
  ├─ F2-B. Type-specific LLM Candidate Classification
  ├─ F2-C. External Exposure Classification
  └─ F2-R. Candidate HVVD Finalization
  ↓
F3. Evidence-aware Similarity Enrichment
  ↓
F4. Source-Code Risk Scoring
  ↓
F6. Evidence-aware HVVD Generation
  ↓
F7. LLM-based Explainable Reporting
```

이 중 F2-A는 OCPP action, payload field, handler, field binding, source-flow-sink, observed check, missing expected check를 정적 분석으로 추출하여 **OCPP-native candidate HVVD fragment**를 생성하는 계층이다.

본 문서의 목적은 다음과 같다.

첫째, F2-A의 역할과 책임 범위를 명확히 정의한다.

둘째, F2-A가 F2-B의 입력 생성용 하위 계층이 아니라, F2-0 Common Code Fact Layer를 공유하는 독립적인 OCPP-native evidence extraction 계층임을 명확히 한다.

셋째, F2-A가 OCPP action/field의 보안 의미를 소스코드 evidence와 연결하는 방식을 정의한다.

넷째, F2-A의 입력, 하위 모듈, 처리 흐름, 출력 스키마, 평가 지표, MVP 적용 전략을 정의한다.

다섯째, C 기반 충전기 synthetic variant를 대상으로 한 초기 구현 전략과 Java 기반 CSMS open-source code 확장 전략을 제시한다.

## 1. F2-A의 역할과 책임 경계

### 1.1 F2-A의 핵심 정의

F2-A는 **OCPP-aware Static Analysis** 계층이다.

F2-A는 일반적인 소스코드 정적 분석 결과를 단순히 취약점 후보로 변환하는 계층이 아니다. F2-A는 OCPP 프로토콜의 action과 payload field가 갖는 보안 의미를 소스코드의 handler, 변수, DTO, sink, check, data-flow evidence와 연결하는 정적 분석 계층이다.

즉, F2-A는 다음 질문에 답한다.

```
이 코드 흐름은 어떤 OCPP action/field에서 출발했는가?

해당 field의 OCPP 보안 의미는 무엇인가?

해당 action/field에 요구되는 expected check는 무엇인가?

코드에서 어떤 observed check가 확인되는가?

어떤 expected check가 누락되었거나 약하게 구현되었는가?

OCPP 문맥상 어떤 root cause, CWE, impact 후보로 연결될 수 있는가?
```

### 1.2 F2-A는 취약점 확정기가 아니다

F2-A의 가장 중요한 설계 원칙은 다음과 같다.

```
F2-A는 취약점 확정기가 아니다.
F2-A는 OCPP-native source-code evidence extraction layer다.
```

F2-A는 정적 분석 기반으로 OCPP-native 취약 후보 evidence를 생성하지만, runtime exploitability 또는 confirmed vulnerability를 확정하지 않는다.

따라서 F2-A의 출력은 다음과 같이 해석해야 한다.

```
OCPP-native candidate
≠ confirmed vulnerability
≠ runtime exploitability confirmed
```

F2-A가 생성하는 결과는 F6. Evidence-aware HVVD Generation에서 HVVD로 구조화될 수 있으며, 이후 필요에 따라 퍼징, 사용자 검토, 유사도 분석, 위험도 산정, 설명형 리포팅의 근거로 사용된다.

### 1.3 F2-A와 F2-B의 관계

F2-A와 F2-B는 상하 관계가 아니다.

F2-A는 F2-B로 넘기기 위한 전처리 계층이 아니며, F2-B는 F2-A의 후속 판단 계층이 아니다. 두 계층은 F2-0 Common Code Fact Layer를 공유하지만 서로 다른 출발점과 분석 목적을 갖는다.

```
F2-A:
OCPP action/field에서 출발
→ OCPP-native candidate HVVD fragment 생성

F2-B:
취약 유형 또는 source-flow-sink evidence에서 출발
→ generic code candidate HVVD fragment 생성
```

F2-A는 OCPP 프로토콜의 의미를 중심으로 분석한다. 예를 들어 `UpdateFirmware.location`이라는 field가 코드에서 `firmware_url` 변수로 바인딩되고, 이후 `system()`에 전달되는 흐름을 추적한다.

반면 F2-B는 `system(cmd)`와 같은 취약 sink 및 command injection 패턴에서 출발하여, 해당 코드가 일반적인 취약 유형에 해당하는지를 Type-specific Detector Package 기반 LLM 후보 분류를 통해 분석한다.

따라서 동일한 코드 흐름이라도 F2-A와 F2-B는 서로 다른 관점의 evidence fragment를 생성할 수 있으며, F2-R에서 병합될 수 있다.

### 1.4 F2-A와 F2-C의 관계

F2-C는 F2-A 후보를 다시 OCPP_REACHABLE로 판정하는 계층이 아니다.

F2-A는 이미 OCPP action/field에서 출발하므로, F2-A의 출력은 기본적으로 OCPP-native candidate이다. 따라서 F2-C가 F2-A 후보에 대해 “OCPP로부터 도달 가능한가?”를 다시 판정하는 것은 역할 중복이다.

F2-C의 주 대상은 F2-B가 생성한 generic code vulnerability candidate이다.

```
F2-C classification target:
  F2-B generic code vulnerability candidate

F2-C reference evidence:
  F2-0 Common Code Fact Layer
  OCPP handler map
  field binding map
  call graph
  data-flow evidence
  external entrypoint map
```

F2-C는 generic 후보가 어떤 외부 입력면을 통해 도달 가능한지를 분류한다.

예를 들어 F2-B가 command injection 후보를 탐지했을 때, F2-C는 해당 후보가 OCPP UpdateFirmware.location에서 도달 가능한지, REST API에서 도달 가능한지, admin UI에서 도달 가능한지, 또는 외부 노출을 확인할 수 없는지를 분류한다.

F2-A의 전체 처리 흐름은 다음과 같다.

```
Source Code Repository
+ F1 OCPP-centric Knowledge Layer
+ F2-0 Common Code Fact Layer
+ Static Analysis Configuration
  ↓
OCPP Source Map Builder
  ↓
OCPP Action Handler Mapping
  ↓

  ↓
OCPP Field Semantic Binding
  ↓

  ↓

  ↓

  ↓

  ↓
Expected Check Matching
  ↓
Missing Check Candidate Generation
  ↓
OCPP-native Evidence Package Generation
  ↓
OCPP_NATIVE_CANDIDATE_HVVD_FRAGMENT
```

F2-A는 코드 전체를 무차별적으로 취약점 관점에서 분석하는 것이 아니라, OCPP action/field와 연결 가능한 코드 흐름을 우선적으로 식별한다.

```

  → source variable
  → source-sink flow
  → observed check
  → missing expected check candidate
  → OCPP-native evidence package
```

## 3. 입력 데이터와 전제 조건

### 3.1 Source Code Repository

F2-A의 분석 대상은 전기차 충전 인프라 관련 소스코드이다.

초기 MVP에서는 C 기반 충전기 synthetic variant를 대상으로 한다. 이후 Java 기반 CSMS open-source code로 확장한다.

```
Phase 1. C 기반 충전기 synthetic variant
Phase 2. Java 기반 CSMS open-source code
```

초기 C 기반 분석 대상은 다음과 같이 구성할 수 있다.

```
C-based Charger Synthetic Variant Set
├─ Firmware Update Module
├─ Diagnostic Command Module
├─ Configuration Parser
├─ MeterValue Parser
├─ OCPP-like Handler Stub
└─ Utility / Shell Wrapper Module
```

Java CSMS 확장 분석 대상은 메시지 방향에 따라 inbound path와 outbound path로 구분한다.

```
Inbound OCPP path:
  Charge Point
    ↓
  OCPP WebSocket / JSON-RPC endpoint
    ↓
  Action Dispatcher
    ↓
  Inbound Action Handler
    ↓
  Request DTO / Payload Field Binding
    ↓
  Service Layer
    ↓
  Repository / Authorization / State / Validation / File Sink

Outbound OCPP path:
  Admin API / Backend Operation / Scheduler / Policy Engine

    ↓
```

### 3.2 F1. OCPP-centric Knowledge Layer

F2-A는 F1 Knowledge Layer를 기준 지식으로 사용한다.

F1은 OCPP action과 payload field의 보안 의미를 정의하고, expected check, dangerous sink domain, root cause, CWE, impact, HVVD generation rule을 구조화한다.

F1의 주요 지식 프로파일은 다음과 같다.

```
OCPP Action Profile
Payload Field Profile
Expected Check Profile
Dangerous Sink Domain Profile
State Profile
Root Cause Taxonomy
Impact Mapping
HVVD Generation Rule
```

예를 들어 `UpdateFirmware.location`은 다음과 같은 보안 의미를 가질 수 있다.

```
Action: UpdateFirmware
Field: location
Semantic Type: firmware_download_url
Trust Level: remote_ocpp_input

Expected Checks:
  - URL_SCHEME_VALIDATION
  - HOST_ALLOWLIST
  - SIGNATURE_VERIFICATION
  - SAFE_DOWNLOAD_API_NO_SHELL

Dangerous Sink Domains:
  - COMMAND_EXECUTION
  - UNSAFE_FIRMWARE_DOWNLOAD
  - UNSAFE_EXTERNAL_RESOURCE

Related CWE:
  - CWE-78
  - CWE-494
  - CWE-345
  - CWE-20
```

F2-A는 이 지식을 이용해 단순 문자열 field인 `location`을 `firmware_download_url`이라는 보안 의미와 연결한다.

### 3.3 F2-0. Common Code Fact Layer

F2-0은 F2-A, F2-B, F2-C가 공통으로 사용하는 코드 사실 계층이다.

F2-0은 언어별 파서, AST, CPG, call graph, data-flow, sink index, check pattern index 등 공통 정적 분석 산출물을 제공한다.

주요 산출물은 다음과 같다.

```
file index
function index
call graph
data-flow candidate
sink index
check pattern index
OCPP handler map
payload field binding map
external entrypoint map
source location index
```

F2-A는 이 중 OCPP handler map, field binding map, source-sink flow candidate, check evidence index, sink index를 집중적으로 사용한다.

### 3.5 Optional Manual Seed

F2-A는 완전 자동 분석을 목표로 하지만, 초기 구현에서는 수동 seed를 허용하는 것이 현실적이다.

수동 seed는 분석 정확도와 재현성을 높이기 위한 보조 입력이다.

```
known OCPP dispatcher
known handler function
known request DTO
known firmware/update module
known command wrapper
known authorization service
known station repository
```

수동 seed는 정적 분석이 탐지하지 못한 dispatcher 또는 framework-specific binding을 보완하는 데 사용된다.

```
OCPP action string
JSON-RPC method field
message dispatcher
handler registration table
handler function
request DTO
payload field access
state transition call
response generation call
```

### 5.4 출력


## 6. OCPP Action Handler Mapping

### 6.1 목적

OCPP Action Handler Mapper는 OCPP action과 실제 코드상의 분석 시작점을 연결한다.

일반적인 inbound OCPP message의 경우 handler function 또는 handler method가 분석 시작점이 되며,

Java CSMS의 outbound remote command action은 command controller, command service, command dispatch path가 분석 시작점이 될 수 있다.

예를 들어 `UpdateFirmware` action이 `handle_update_firmware()` 함수로 전달되는 경우, 이 매핑은 F2-A의 후속 field binding 및 source-sink flow 분석의 출발점이 된다.

### 6.2 C 기반 충전기 Handler Mapping

C 기반 충전기에서는 다음 패턴을 우선 고려한다.

```
if/else 기반 action dispatch
switch/case 기반 action dispatch
function pointer table
string-to-handler map
manual registration table
OCPP-like handler stub
```

예시는 다음과 같다.

```c
if (strcmp(action, "UpdateFirmware") == 0) {
    handle_update_firmware(req);
}
```

또는 다음과 같은 function pointer table을 고려할 수 있다.

```c
static ocpp_handler_t handlers[] = {
    {"UpdateFirmware", handle_update_firmware},
    {"ChangeConfiguration", handle_change_configuration}
};
```

F2-A는 action string과 handler function의 연결 evidence를 생성한다.

### 6.3 Java CSMS Action Mapping

Java CSMS에서는 OCPP message direction에 따라 action mapping 방식을 구분한다.

#### 6.3.1  Inbound Action Handler Mapping

Inbound action은 Charge Point가 CSMS로 전송하는 OCPP 요청 또는 상태 메시지를 처리하는 handler에 매핑된다.

```
WebSocket endpoint
JSON-RPC dispatcher
annotation-based handler
method name convention
DTO class mapping
service routing
```

예시는 다음과 같다.

```java
@OcppAction("Authorize")
public AuthorizeResponse handle(AuthorizeRequest req) {
    return authorizeService.authorize(req);
}
```

또는 dispatcher 기반 구조도 고려한다.

```java
handlerRegistry.get(action).handle(payload);
```

#### 6.3.2 Outbound Command Path Mapping

Outbound action은 CSMS가 Charge Point로 전송하는 remote command를 생성·전송하는 command service path에 매핑된다. 이 경우 `Action Handler`라는 표현을 사용하지 않고, command controller, command service, command builder, command dispatch service를 분석 대상으로 본다.

```
Admin API endpoint
Backend operation
Scheduler
Command controller
Command service
OCPP command builder
Command dispatch service
```

예시는 다음과 같다.

```java
public RemoteStartTransactionResponse remoteStart(RemoteStartCommandRequest req) {
    return remoteStartCommandService.start(req);
}
```

```java
public void start(RemoteStartCommandRequest req) {
    commandService.sendRemoteStartCommand(
        req.getChargePointId(),
        req.getConnectorId(),
        req.getIdTag()
    );
}
```

### 6.4 출력

```json
{
  "handler_map_id": "OCPP-HMAP-0001",
  "action": "UpdateFirmware",
  "handler": {
    "language": "C",
    "file": "firmware_update.c",
    "function": "handle_update_firmware",
    "line": 31
  },
  "mapping_evidence": [
    {
      "type": "DISPATCH_STRING_MATCH",
      "value": "UpdateFirmware",
      "file": "dispatcher.c",
      "line": 18
    }
  ],
  "confidence": 0.91
}
```

## 7. Payload Field Source Extraction

### 7.1 목적

Payload Field Source Extractor는 OCPP payload field가 코드 내 변수, 구조체 필드, DTO property, getter, map access, JSON parser 결과와 어떻게 연결되는지 식별한다.

이 단계는 OCPP field를 실제 data-flow source로 전환하는 핵심 단계이다.

### 7.2 C 구조체/JSON parser 기반 Field Binding

C 기반 충전기에서는 다음 패턴을 고려한다.

```
struct field access
JSON object field extraction
string copy into local variable
request object field alias
pointer alias
wrapper parser function
```

## 9. Interprocedural Source-Sink Flow Analysis

### 9.1 목적

Interprocedural Source-Sink Flow Analyzer는 OCPP payload field에서 시작한 source variable이 함수 간 호출을 거쳐 dangerous sink에 도달하는지 분석한다.

이 모듈은 F2-A의 핵심 정적 분석 엔진이다.

### 9.2 분석 대상

```
local assignment
parameter passing
return value propagation
global variable propagation
struct field propagation
DTO object propagation
wrapper/helper function propagation
callback/function pointer path
service layer propagation
repository/file/process/network sink path
```

### 9.3 C 기반 흐름 예시

```
UpdateFirmware.location
  → req->location
  → firmware_url
  → download_firmware(firmware_url)
  → sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url)
  → system(cmd)
```

### 9.4 Java CSMS 흐름 예시

Java CSMS의 inbound OCPP path에서는 `Authorize`, `StartTransaction`, `MeterValues`, `StopTransaction`과 같이 Charge Point에서 CSMS로 전달되는 action을 중심으로 source-flow-decision point를 추적한다.

예를 들어 `Authorize.idTag` 흐름은 다음과 같이 분석할 수 있다.

```
  Authorize.req.idTag
  → request.getIdTag()
  → authorizeService.authorize(idTag)
  → authorizationRepository.findByIdTag(idTag)
  → AuthorizationDecision
```

Java CSMS의 경우 sink가 반드시 command execution일 필요는 없다.

`AuthorizationDecision`, transaction state transition, connector state update, repository write, remote command dispatch, external resource access와 같은 security-sensitive decision point 또는 state-changing operation도 F2-A의 sink 또는 decision point로 해석될 수 있다.

따라서 authorization check 누락, station ownership check 누락, connector availability check 누락, transaction state check 누락도 OCPP-native 취약 후보의 핵심 근거가 될 수 있다. 다만 F2-A는 이를 취약점 확정으로 판단하지 않고, expected check 대비 observed check가 충분한지 비교하여 missing / weak / unverified check candidate로 생성한다.

### 9.5 출력

```json
{
  "flow_id": "OCPP-FLOW-0001",
  "action": "UpdateFirmware",
  "field": "location",
  "source": {
    "variable": "firmware_url",
    "file": "firmware_update.c",
    "function": "handle_update_firmware",
    "line": 42
  },
  "flow": [
    {
      "function": "handle_update_firmware",
      "operation": "firmware_url = req->location"
    },
    {
      "function": "download_firmware",
      "operation": "sprintf(cmd, \"wget %s -O /tmp/fw.bin\", firmware_url)"
    },
    {
      "function": "download_firmware",
      "operation": "system(cmd)"
    }
  ],
  "sink_candidate": {
    "api": "system",
    "sink_domain": "COMMAND_EXECUTION"
  },
  "confidence": 0.82
}
```

## 11. Observed Check Detection

### 11.1 목적

Observed Check Detection은 OCPP action/field에서 출발한 source value가 dangerous sink 또는 security-sensitive decision point에 도달하기 전에 코드상에서 실제로 수행된 검증, 인증, 권한 확인, 상태 확인, 무결성 검증, sanitization, safe API 사용 여부를 식별하는 단계이다.

F2-A에서 Observed Check Detection은 단순히 `if` 조건문이나 validation 함수 호출을 찾는 작업이 아니다. 이 단계의 목적은 코드에 존재하는 검증 evidence가 F1. OCPP-centric Knowledge Layer에서 정의한 expected check 중 어떤 의미에 대응하는지를 해석하는 것이다.

예를 들어 `UpdateFirmware.location` 필드에 대해 코드에서 `if (firmware_url == NULL)`이 확인되었다면 이는 `NULL_CHECK`로 볼 수 있다. 그러나 이것만으로 `URL_SCHEME_VALIDATION`, `HOST_ALLOWLIST`, `SIGNATURE_VERIFICATION`, `SAFE_DOWNLOAD_API_NO_SHELL`이 충족되었다고 볼 수는 없다.

또한 Java CSMS에서 `stationAccessPolicy.canControl(operatorId, chargePointId)`와 같은 함수 호출이 발견되었을 때, 단순 rule 기반 분석만으로 이것이 `STATION_OWNERSHIP_CHECK`인지, `OPERATOR_PERMISSION_CHECK`인지, 또는 단순 null check인지 판단하기 어려울 수 있다. 이러한 경우 F2-A는 선택적으로 LLM-assisted Check Semantics Classification을 사용한다.

따라서 F2-A의 Observed Check Detection은 다음 두 축으로 구성된다.

```
Observed Check Detection
├─ Rule-based Observed Check Detection
└─ LLM-assisted Check Semantics Classification
```

다만 여기서 LLM은 취약점 확정기가 아니다. LLM은 코드 evidence가 F1 Expected Check Profile의 어떤 expected check에 의미적으로 대응하는지 분류하는 **Validation Checker**로만 사용된다.

즉, F2-A에서 LLM의 역할은 다음과 같다.

```
허용되는 역할:
- observed check candidate 분류
- expected check와 observed check의 의미적 매칭 보조
- weak / partial check 여부 판정
- check confidence 및 limitation 생성

허용되지 않는 역할:
- 취약점 확정
- runtime exploitability 판단
- confirmed HVVD 생성
- 최종 위험도 판정
```

---

### 11.2 Observed Check Detection의 전체 구조

Observed Check Detection은 다음 하위 모듈로 구성된다.

```
F2-A7. Observed Check Detection
├─ F2-A7-1. Rule-based Check Pattern Detector
├─ F2-A7-2. Check Evidence Context Builder
├─ F2-A7-3. LLM-assisted Check Semantics Classifier
├─ F2-A7-4. Weak / Partial Check Classifier
└─ F2-A7-5. Observed Check Confidence Annotator
```

각 모듈의 역할은 다음과 같다.

```
Rule-based Check Pattern Detector:
  코드에서 명시적인 validation, authorization, state check, integrity check 패턴을 탐지한다.

Check Evidence Context Builder:
  LLM 또는 후속 matcher가 사용할 수 있도록 check 주변 코드, control-flow, call-site, argument binding, field semantic, expected check profile을 evidence package로 구성한다.

LLM-assisted Check Semantics Classifier:
  rule 기반으로 의미 판정이 어려운 check evidence가 어떤 expected check에 대응하는지 분류한다.

Weak / Partial Check Classifier:
  관찰된 check가 expected check를 충분히 만족하는지, 일부만 만족하는지, 단순 weak check인지 판정한다.

Observed Check Confidence Annotator:
  rule 기반 결과와 LLM-assisted 결과의 신뢰도, 충돌 여부, 한계를 기록한다.
```

---

### 11.3 Rule-based Observed Check Detection

Rule-based Observed Check Detection은 정적 분석으로 확인 가능한 명시적 패턴을 우선 탐지한다.

이 방식은 재현성이 높고 설명 가능성이 높기 때문에 F2-A의 기본 탐지 방식으로 사용된다. 특히 C 기반 충전기 MVP에서는 rule 기반 탐지가 핵심이 된다.

주요 탐지 대상은 다음과 같다.

```
NULL_CHECK
TYPE_CHECK
RANGE_CHECK
LENGTH_CHECK
FORMAT_CHECK
URL_SCHEME_CHECK
HOST_ALLOWLIST_CHECK
PATH_TRAVERSAL_CHECK
SIGNATURE_VERIFICATION
HASH_VERIFICATION
AUTHORIZATION_CHECK
OWNERSHIP_CHECK
STATE_CHECK
CONNECTOR_AVAILABILITY_CHECK
TRANSACTION_EXISTENCE_CHECK
SAFE_API_USAGE
SHELL_ESCAPE_CHECK
```

Rule-based detector는 다음 evidence를 기반으로 observed check candidate를 생성한다.

```
condition expression
function call name
callee summary
argument binding
control-flow dominance
source-to-check relation
check-to-sink ordering
known validation API pattern
known authorization service pattern
known state check pattern
```

예를 들어 다음 C 코드는 `NULL_CHECK`로 탐지된다.

```c
if (firmware_url == NULL) {
    return;
}
```

이 경우 F2-A는 다음 observed check candidate를 생성한다.

```json
{
  "observed_check_id": "OCPP-OBS-CHK-0001",
  "detection_method": "RULE_BASED",
  "check_type": "NULL_CHECK",
  "action": "UpdateFirmware",
  "field": "location",
  "applies_to": [
    "firmware_url"
  ],
  "file": "firmware_update.c",
  "function": "handle_update_firmware",
  "line": 11,
  "evidence": "if (firmware_url == NULL)",
  "confidence": 0.95
}
```

반면 다음 C 코드는 `SAFE_DOWNLOAD_API_NO_SHELL`을 만족하지 않는 negative evidence로 기록될 수 있다.

```c
sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url);
system(cmd);
```

이 경우 observed check가 아니라 unsafe sink usage evidence로 기록된다.

```json
{
  "evidence_id": "OCPP-NEG-CHK-0001",
  "evidence_type": "NEGATIVE_CHECK_EVIDENCE",
  "related_expected_check": "SAFE_DOWNLOAD_API_NO_SHELL",
  "reason": "The firmware URL is concatenated into a shell command and passed to system(cmd).",
  "file": "firmware_update.c",
  "function": "download_firmware",
  "line": 22,
  "confidence": 0.94
}
```

```
call-site summary
callee function name
argument binding
```

### 11.5 LLM-assisted Check Semantics Classification

LLM-assisted Check Semantics Classification은 정적 패턴만으로 의미 해석이 어려운 observed check candidate에 대해 선택적으로 수행한다.

LLM-assisted Check Semantics Classification은 모든 observed check에 대해 수행하지 않는다.

다음 조건 중 하나에 해당할 때만 선택적으로 호출한다.

- rule 기반으로 check type을 확정하기 어려운 경우
- wrapper/helper 함수명이 도메인 의미를 포함하지만 내부 구현이 불완전하게 분석된 경우
- service-layer authorization 또는 policy check 의미 판정이 필요한 경우
- observed check가 expected check와 strong/partial/weak 중 어디에 해당하는지 불명확한 경우
- rule 기반 결과와 expected check matching 결과가 충돌하거나 confidence가 낮은 경우

LLM은 코드 evidence가 F1 Expected Check Profile의 어떤 expected check에 대응하는지 분류한다. 특히 다음 경우에 유용하다.

```
framework-specific authorization function
custom policy service call
wrapper/helper validation function
domain-specific state check
repository 기반 ownership check
service-layer permission check
configuration 기반 allowlist check
```

예를 들어 다음 Java 코드가 있다고 가정한다.

```java
if (!stationAccessPolicy.canControl(operatorId, chargePointId)) {
    return RemoteStartTransactionResponse.rejected();
}
```

LLM-assisted classifier는 다음 결과를 생성할 수 있다.

```json
{
  "observed_check_id": "OCPP-LLM-OBS-CHK-0001",
  "detection_method": "LLM_ASSISTED",
  "evidence": "stationAccessPolicy.canControl(operatorId, chargePointId)",
  "observed_check_candidate": "STATION_OWNERSHIP_CHECK",
  "matched_expected_check": "STATION_OWNERSHIP_CHECK",
  "check_strength": "STRONG",
  "confidence": 0.86,
  "rationale": "The function name and arguments indicate that the operator's control permission over the target charge point is checked before remote command dispatch.",
  "limitations": [
    "The internal implementation of stationAccessPolicy.canControl was not analyzed in this evidence package."
  ]
}
```

반대로 다음 코드는 `IDTAG_AUTHORIZATION_CHECK`가 아니라 `NULL_CHECK`로만 분류된다.

```java
if (request.getIdTag() == null) {
    return RemoteStartTransactionResponse.rejected();
}
```

LLM-assisted classifier는 다음과 같은 결과를 생성할 수 있다.

```json
{
  "observed_check_id": "OCPP-LLM-OBS-CHK-0002",
  "detection_method": "LLM_ASSISTED",
  "evidence": "if (request.getIdTag() == null)",
  "observed_check_candidate": "NULL_CHECK",
  "matched_expected_check": null,
  "check_strength": "WEAK",
  "confidence": 0.91,
  "rationale": "The code checks only whether idTag is present. It does not verify whether the idTag is authorized for charging.",
  "limitations": [
    "This check does not satisfy IDTAG_AUTHORIZATION_CHECK.",
    "This check does not satisfy STATION_OWNERSHIP_CHECK or CONNECTOR_AVAILABILITY_CHECK."
  ]
}
```

### 11.6 Weak / Partial Check 판정

Observed Check Detection은 단순히 check의 존재 여부만 기록하지 않는다. 관찰된 check가 expected check를 충분히 만족하는지, 일부만 만족하는지, 또는 weak check에 해당하는지도 기록한다.

F2-A는 check strength를 다음과 같이 분류한다.

```
STRONG:
  expected check의 의미를 충분히 만족하는 evidence가 확인됨

PARTIAL:
  expected check의 일부 조건은 만족하지만 충분하지 않음

WEAK:
  단순 존재 확인, null check, 형식 확인 등 보안 의미가 제한적임

UNKNOWN:
  check로 보이는 evidence는 있으나 의미 판정이 불충분함

CONFLICTED:
  rule 기반 결과와 LLM-assisted 결과가 충돌함
```

예를 들어 `UpdateFirmware.location`에 대해 HTTPS scheme만 확인하는 코드는 `URL_SCHEME_VALIDATION`은 일부 만족할 수 있지만, `HOST_ALLOWLIST`나 `SIGNATURE_VERIFICATION`을 만족하지 않는다.

```c
if (strncmp(firmware_url, "https://", 8) != 0) {
    return;
}
```

이 경우 결과는 다음과 같이 표현할 수 있다.

```json
{
  "observed_check_id": "OCPP-OBS-CHK-URL-0001",
  "check_type": "URL_SCHEME_VALIDATION",
  "matched_expected_check": "URL_SCHEME_VALIDATION",
  "check_strength": "STRONG",
  "evidence": "strncmp(firmware_url, \"https://\", 8) != 0",
  "limitations": [
```

### 11.8 LLM 사용 제한사항

F2-A에서 LLM-assisted Check Semantics Classification을 사용할 때는 다음 제한사항을 반드시 적용한다.

첫째, LLM 입력은 원시 소스코드 전체가 아니라 F2-0 Common Code Fact Layer가 추출한 제한된 evidence package여야 한다.

둘째, LLM 출력은 check semantics classification으로 제한한다.

셋째, LLM은 취약점 확정, exploitability 판단, 최종 위험도 산정, lifecycle state 확정을 수행하지 않는다.

넷째, LLM 결과는 항상 confidence와 limitation을 포함해야 한다.

다섯째, rule 기반 결과와 LLM-assisted 결과가 충돌하는 경우 `CONFLICTED` 또는 `REVIEW_REQUIRED`로 표시한다.

여섯째, LLM이 특정 expected check를 만족한다고 판단하더라도, 내부 구현이 분석되지 않은 helper function이나 외부 policy service는 limitation으로 명시해야 한다.

권장 제한 규칙은 다음과 같다.

```
LLM allowed output:
  - observed_check_candidate
  - matched_expected_check
  - check_strength
  - confidence
  - rationale
  - limitations

LLM forbidden output:
  - confirmed vulnerability
  - exploitability verdict
  - final risk score
  - lifecycle state confirmation
  - remediation certainty
```

## 12. Expected Check Matching 및 Missing Check Candidate 생성

### 12.1 목적

Expected Check Matching 및 Missing Check Candidate 생성 단계는 F1. OCPP-centric Knowledge Layer에서 정의한 expected check와 F2-A7 Observed Check Detection이 생성한 observed check candidates를 비교하여, 확인되지 않았거나 불충분한 expected check를 missing check candidate로 생성하는 단계이다.

이 단계의 핵심 목적은 다음과 같다.

```
F1이 요구하는 expected check
  vs.
F2-A7이 관찰한 observed check candidate

비교 결과:
  - satisfied expected check
  - partially satisfied expected check
  - weakly related check
  - unverified expected check
  - missing check candidate
```

중요한 점은 F2-A가 missing check를 확정 단정하지 않는다는 것이다.

```
Missing check는 단정이 아니라 candidate로 표현한다.
```

정적 분석은 코드의 모든 실행 경로, 외부 policy enforcement, gateway authorization, runtime configuration, framework interceptor, deployment-specific control을 완전히 확인할 수 없다. 따라서 F2-A는 “누락 확정”이 아니라 “정적 evidence 기준으로 확인되지 않은 expected check 후보”를 생성한다.

---

### 12.2 입력

Expected Check Matching의 입력은 다음과 같다.

```
F1 OCPP Action Profile
F1 Payload Field Profile
F1 Expected Check Profile
F1 Dangerous Sink Domain Profile
F2-A source-sink flow candidate
F2-A observed check analysis
F2-A negative check evidence
F2-A static confidence metadata
```

구조적으로는 다음과 같이 연결된다.

```
OCPP action/field
  → F1 expected check list
  → F2-A observed check candidates
  → check strength 판단
  → expected check matching
  → missing check candidate 생성
```

예를 들어 `UpdateFirmware.location`의 F1 expected check는 다음과 같다.

```
URL_SCHEME_VALIDATION
HOST_ALLOWLIST
SIGNATURE_VERIFICATION
SAFE_DOWNLOAD_API_NO_SHELL
```

F2-A7에서 관찰된 check가 `NULL_CHECK`뿐이라면, 위 expected check들은 모두 missing check candidate 또는 unverified expected check로 남는다.

---

### 12.3 Expected Check Matching 기준

Expected Check Matching은 단순 문자열 매칭만으로 수행하지 않는다.

F2-A는 다음 matching 기준을 사용한다.

```
Exact Match:
  observed_check_candidate가 expected_check와 직접 일치

Semantic Match:
  observed check의 의미가 expected check와 대응

Equivalent Helper Match:
  helper/wrapper function이 expected check를 수행한다고 볼 수 있음

Policy Service Match:
  authorization/policy service 호출이 expected check에 대응

Partial Match:
  expected check의 일부 조건만 만족

Weak Match:
  관련은 있으나 expected check를 만족한다고 보기 어려움

Negative Evidence:
  expected check와 반대되는 unsafe evidence가 존재

Unknown:
  check 여부를 판단할 evidence가 부족
```

예시는 다음과 같다.

```
observed: validateUrlScheme(firmware_url)
expected: URL_SCHEME_VALIDATION
→ Exact 또는 Semantic Match

observed: stationAccessPolicy.canControl(operatorId, chargePointId)
expected: STATION_OWNERSHIP_CHECK
→ Semantic 또는 Policy Service Match

observed: if (idTag != null)
expected: IDTAG_AUTHORIZATION_CHECK
→ Weak Match 또는 No Match

observed: system(cmd)
expected: SAFE_DOWNLOAD_API_NO_SHELL
→ Negative Evidence
```

---

### 12.4 Check Matching 상태값

Expected Check Matching 결과는 다음 상태값 중 하나로 표현한다.

```
SATISFIED:
  expected check를 충족하는 충분한 evidence가 확인됨

PARTIALLY_SATISFIED:
  expected check의 일부 조건은 확인되었으나 충분하지 않음

WEAKLY_RELATED:
  관련 check는 있으나 expected check를 만족한다고 보기 어려움

UNVERIFIED:
  expected check 수행 여부를 확인할 evidence가 없음

NEGATIVE_EVIDENCE_FOUND:
  expected check와 반대되는 unsafe evidence가 확인됨

CONFLICTED:
  rule-based 결과와 LLM-assisted 결과가 충돌함

REVIEW_REQUIRED:
  자동 판정 신뢰도가 낮아 사용자 또는 분석자 검토가 필요함
```

이 상태값은 missing check candidate 생성에 사용된다.

---

### 12.5 Missing Check Candidate 생성 규칙

F2-A는 다음 규칙에 따라 missing check candidate를 생성한다.

```
SATISFIED:
  missing check candidate로 생성하지 않음

PARTIALLY_SATISFIED:
  weak_or_partial_check_candidate로 생성

WEAKLY_RELATED:
  missing check candidate로 유지하되 observed weak check를 함께 기록

UNVERIFIED:
  missing check candidate로 생성

NEGATIVE_EVIDENCE_FOUND:
  high-confidence missing check candidate로 생성

CONFLICTED:
  review_required_missing_check_candidate로 생성

REVIEW_REQUIRED:
  review_required로 표시
```

즉, missing check candidate는 단일 목록이 아니라 원인과 신뢰도에 따라 구분된다.

```
missing_check_candidates
weak_or_partial_check_candidates
unverified_check_candidates
negative_evidence_based_missing_candidates
review_required_missing_check_candidates
```

이 구분은 F6. Evidence-aware HVVD Generation에서 HVVD의 limitation과 confidence를 생성할 때 중요하게 사용된다.

### 12.8 Rule-based 결과와 LLM-assisted 결과의 충돌 처리

F2-A는 rule 기반 결과와 LLM-assisted 결과가 항상 일치한다고 가정하지 않는다.

충돌이 발생하는 경우 다음과 같이 처리한다.

```
Case 1. Rule-based detector는 expected check로 판단했으나 LLM은 weak check로 판단
  → CONFLICTED 또는 REVIEW_REQUIRED

Case 2. LLM은 expected check로 판단했으나 rule evidence가 부족
  → PARTIALLY_SATISFIED 또는 REVIEW_REQUIRED

Case 3. Rule과 LLM 모두 동일 expected check로 판단
  → SATISFIED, confidence 상향 가능

Case 4. Rule과 LLM 모두 check 부재로 판단
  → UNVERIFIED 또는 missing_check_candidate
```

### 12.10 F6 연계

F2-A의 Missing Check Candidate 결과는 F6. Evidence-aware HVVD Generation에서 root cause candidate와 HVVD lifecycle state hint를 생성하는 데 사용된다.

예를 들어 `UpdateFirmware.location`에서 다음 조건이 충족되었다고 가정한다.

```
field_semantic = firmware_download_url
sink_domain = COMMAND_EXECUTION
missing_check_candidates contains SAFE_DOWNLOAD_API_NO_SHELL
missing_check_candidates contains URL_SCHEME_VALIDATION
```

F6는 이를 다음과 같은 root cause candidate로 연결할 수 있다.

```
untrusted_firmware_url_to_shell_command
missing_firmware_url_policy_validation
missing_firmware_integrity_verification
```

단, F2-A의 missing check candidate는 F6에서도 confirmed vulnerability로 직접 승격되지 않는다. F6는 이를 `STATIC_SUSPECT_HVVD` 또는 `REVIEW_READY_HVVD`의 근거로 사용하며, runtime evidence가 없는 경우 confirmed 상태로 전환하지 않는다.

### 12.11 설계 원칙 요약

Expected Check Matching 및 Missing Check Candidate 생성 단계의 원칙은 다음과 같다.

```
1. F1 expected check와 F2-A observed check candidate를 비교한다.

2. observed check candidate는 rule-based detector와 LLM-assisted classifier에서 생성될 수 있다.

3. LLM 결과는 check semantics evidence이며, 취약점 확정 근거가 아니다.

4. Missing check는 확정이 아니라 candidate로 표현한다.

5. Weak check와 partial check는 missing check와 분리해서 기록한다.

6. Negative evidence가 있는 경우 높은 confidence의 missing check candidate로 기록할 수 있다.

7. Rule과 LLM 결과가 충돌하면 REVIEW_REQUIRED로 표시한다.

8. 모든 결과는 file/function/line/evidence_id로 추적 가능해야 한다.

9. Runtime exploitability와 confirmed vulnerability는 F2-A가 판단하지 않는다.

10. F6는 이 결과를 evidence-aware HVVD 생성의 근거로 사용한다.
```

## 14. Static Confidence Annotation

### 14.1 목적

Static Confidence Annotator는 F2-A가 생성한 후보 evidence에 대해 정적 분석 신뢰도를 부여한다.

이 confidence는 취약점 심각도 점수가 아니다. 정적 evidence의 연결 품질을 나타내는 지표이다.

```
static_confidence
≠ vulnerability severity
≠ exploitability score
```

### 14.2 Confidence 산정 요소

F2-A의 static confidence는 다음 요소를 기반으로 산정한다.

```
handler mapping confidence
field binding confidence
semantic binding confidence
source-sink flow confidence
sink mapping confidence
observed check detection confidence
expected/missing check matching confidence
source location traceability
```

예시 가중치는 다음과 같이 구성할 수 있다.

```
handler mapping: 0.15
field binding: 0.20
semantic binding: 0.15
source-sink flow: 0.25
sink mapping: 0.10
check evidence: 0.10
traceability: 0.05
```

### 14.3 Confidence 해석

```
0.80 이상:
  high-confidence OCPP-native static candidate

0.60 이상 0.80 미만:
  moderate-confidence OCPP-native static candidate

0.40 이상 0.60 미만:
  weak but reviewable static candidate

0.40 미만:
  low-confidence candidate 또는 보류
```

## 16. F2-B/F2-C/F2-R/F6 연계 인터페이스

### 16.1 F2-B와의 연계

F2-A와 F2-B는 독립 분석 계층이지만, 동일한 코드 흐름을 서로 다른 관점에서 분석할 수 있다.

예를 들어 다음 흐름이 있다고 가정한다.

```
firmware_url
  → sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url)
  → system(cmd)
```

F2-A는 이 흐름을 다음과 같이 해석한다.

```
UpdateFirmware.location
→ firmware_download_url
→ missing URL/SIGNATURE/SAFE_DOWNLOAD checks
→ OCPP-native candidate
```

F2-B는 같은 흐름을 다음과 같이 해석한다.

```
untrusted input to system()
→ command injection likely
→ generic code candidate
```

따라서 F2-R은 두 결과를 병합하여 더 풍부한 candidate HVVD를 생성할 수 있다.

### 16.2 F2-C와의 연계

F2-C는 F2-B generic 후보의 external exposure를 분류한다.

F2-A 후보는 이미 OCPP-native candidate이므로 F2-C가 다시 OCPP_REACHABLE 여부를 판정하지 않는다.

F2-C의 결과 예시는 다음과 같다.

```
EXTERNAL_EXPOSED + OCPP
EXTERNAL_EXPOSED + REST_API
EXTERNAL_EXPOSED + ADMIN_UI
INTERNAL_ONLY
UNKNOWN_EXPOSURE
```

### 16.3 F2-R과의 연계

F2-R은 F2-A, F2-B, F2-C의 결과를 통합하여 Finalized Candidate HVVD Set을 생성한다.

```
Finalized Candidate HVVD Set
├─ OCPP-native Candidate HVVD
├─ External-exposed Generic Candidate HVVD
│  ├─ OCPP-exposed Generic Candidate HVVD
│  ├─ REST/API-exposed Generic Candidate HVVD
│  ├─ Admin/UI-exposed Generic Candidate HVVD
│  └─ CLI/OTA-exposed Generic Candidate HVVD
└─ Internal-only Generic Candidate HVVD
```

### 16.4 F6와의 연계

F6는 F2-A가 생성한 OCPP-native candidate fragment와 evidence package를 기반으로 evidence-aware HVVD를 생성한다.

F6는 F2-A evidence를 사용해 다음 정보를 구조화한다.

```
vulnerability hypothesis
OCPP context
source code evidence
root cause candidate
missing check evidence
impact candidate
CWE mapping
lifecycle state
confidence
limitation
```

F2-A의 출력은 F6에서 초기 HVVD 후보 상태를 구성하는 근거로 사용된다.

정적 evidence만 있는 경우 기본 상태는 STATIC_SUSPECT_HVVD 또는 REVIEW_READY_HVVD로 해석한다.

CONFIRMED_HVVD, DISMISSED_HVVD, UNREACHED_RISK_HVVD, GUARDED_FLOW_HVVD 등은

F5 runtime validation, fuzzing evidence, runtime reachability evidence, guarded-flow evidence 등

추가 검증 결과가 있을 때만 부여될 수 있다.

단, F2-A 자체는 lifecycle 확정 판단을 수행하지 않는다.

## 18. Java CSMS 확장 적용 예시

## 18.1 Java CSMS 분석 구조: Inbound / Outbound 분리

Java CSMS에서 F2-A는 OCPP action/field의 보안 의미를 Java 코드의 handler, DTO field, service flow, authorization/state decision point, sink evidence와 연결한다.

다만 Java CSMS의 OCPP 처리 구조는 메시지 방향에 따라 명확히 구분해야 한다.

```
Inbound OCPP path:
  Charge Point → CSMS

Outbound OCPP path:
  CSMS → Charge Point
```

F2-A는 두 방향 모두 분석할 수 있지만, 분석 출발점과 코드 구조가 다르므로 하나의 흐름으로 섞어 표현하지 않는다.

---

## 18.1.1 Inbound OCPP 분석 구조: Charge Point → CSMS

Inbound OCPP path는 Charge Point가 CSMS로 전송하는 OCPP 요청 또는 상태 메시지를 처리하는 코드 경로이다.

대표 action은 다음과 같다.

```
BootNotification
Authorize
StartTransaction
MeterValues
StopTransaction
StatusNotification
FirmwareStatusNotification
DiagnosticsStatusNotification
DataTransfer
```

Inbound 구조는 다음과 같다.

```
Charge Point
  ↓
OCPP WebSocket / JSON-RPC endpoint
  ↓
Action Dispatcher
  ↓
Inbound Action Handler
  ↓
Request DTO
  ↓
DTO Field Getter
  ↓
Service Layer
  ↓
Repository / Authorization / State / Validation / File Sink
```

이 구조에서 F2-A는 다음을 분석한다.

```
OCPP inbound action
  → request payload field
  → DTO field binding
  → service parameter propagation
  → authorization decision
  → state transition
  → repository update
  → observed check
  → expected check matching
  → missing check candidate
```

예를 들어 `Authorize.idTag`는 단순 문자열이 아니라 충전 권한 판단에 사용되는 authorization identifier이다. F2-A는 이 field가 authorization service, account status check, authorization decision enforcement와 어떻게 연결되는지 분석한다.

---

## 18.1.2 Outbound OCPP 분석 구조: CSMS → Charge Point

Outbound OCPP path는 CSMS가 Charge Point로 원격 명령 또는 제어 메시지를 생성·전송하는 코드 경로이다.

대표 action은 다음과 같다.

```
RemoteStartTransaction
RemoteStopTransaction
UnlockConnector
Reset
ChangeConfiguration
UpdateFirmware
GetDiagnostics
TriggerMessage
```

Outbound 구조는 inbound handler 구조와 다르다.

```
Admin API / Backend Operation / Scheduler / Policy Engine
  ↓
CSMS Command Controller or Service
  ↓
Command Request DTO
  ↓
Authorization / Ownership / State Check
  ↓
OCPP Command Builder
  ↓
Command Dispatch Service
  ↓
Charge Point
```

이 구조에서 F2-A는 다음을 분석한다.

```
OCPP outbound action
  → command input field
  → service parameter propagation
  → authorization / ownership / state check
  → command generation
  → command dispatch sink
  → observed check
  → expected check matching
  → missing check candidate
```

Outbound action의 경우 `Action Handler`라는 표현을 무리하게 사용하지 않는다. 대신 `Command Controller`, `Command Service`, `Command Builder`, `Command Dispatch Service`와 같은 코드 요소를 분석 대상으로 본다.

### 19.1 F2-A 단독 평가 지표

F2-A의 평가 지표는 취약점 확정 성능이 아니라 OCPP-native evidence extraction의 정확성과 추적성을 중심으로 구성한다.

```
- Handler Mapping Accuracy
- Field Binding Accuracy
- Field Semantic Binding Accuracy
- Source-Sink Flow Precision / Recall
- Dangerous Sink Mapping Accuracy
- Observed Check Detection Accuracy
- LLM-assisted Check Semantics Classification Accuracy
- Expected Check Matching Accuracy
- Weak / Partial Check Classification Accuracy
- Missing Check Classification Accuracy
- Rule-vs-LLM Conflict Handling Accuracy
- Static Evidence Completeness
- Static Evidence Traceability
```

### 19.2 지표별 의미

Handler Mapping Accuracy는 OCPP action이 올바른 handler function 또는 method에 매핑되었는지를 측정한다.

Field Binding Accuracy는 OCPP payload field가 코드 내 변수, 구조체 필드, DTO property, getter에 올바르게 연결되었는지를 측정한다.

Field Semantic Binding Accuracy는 OCPP field가 F1 Knowledge Layer의 semantic type과 올바르게 연결되었는지를 측정한다.

Source-Sink Flow Precision / Recall은 OCPP field source에서 dangerous sink 또는 decision point까지의 흐름 후보 탐지 정확도를 측정한다.

Dangerous Sink Mapping Accuracy는 탐지된 sink가 올바른 sink domain 및 CWE 후보와 연결되었는지를 측정한다.

Observed Check Detection Accuracy는 코드에 존재하는 검증, 인증, 권한, 상태 확인 로직을 올바르게 탐지했는지를 측정한다.

LLM-assisted Check Semantics Classification Accuracy는 rule 기반으로 의미 판정이 어려운 observed check candidate에 대해 LLM-assisted Validation Checker가 expected check 의미와 check strength를 올바르게 분류했는지를 측정한다.

Expected Check Matching Accuracy는 F1 KB가 정의한 expected check와 F2-A가 탐지한 observed check를 올바르게 매칭했는지를 측정한다.

Weak / Partial Check Classification Accuracy는 관찰된 check가 expected check를 충분히 만족하는지, 일부만 만족하는지, 또는 weak check에 해당하는지를 올바르게 구분했는지를 측정한다.

Missing Check Classification Accuracy는 expected check와 observed check를 비교하여 누락 후보를 적절하게 산출했는지를 측정한다.

Rule-vs-LLM Conflict Handling Accuracy는 rule 기반 결과와 LLM-assisted 결과가 충돌하는 경우 이를 SATISFIED로 과도하게 확정하지 않고, CONFLICTED 또는 REVIEW_REQUIRED 등 적절한 상태로 처리했는지를 측정한다.

Static Evidence Traceability는 모든 후보가 file, function, line, evidence_id로 추적 가능한지를 측정한다.

## 20. 한계와 향후 확장

### 20.1 한계

F2-A는 정적 분석 기반 계층이므로 다음 한계를 갖는다.

첫째, runtime exploitability를 확정할 수 없다.

둘째, framework-specific dynamic dispatch를 완전히 해석하지 못할 수 있다.

셋째, 설정 파일, DB 정책, 외부 policy server에서 수행되는 검증을 코드만으로 확인하지 못할 수 있다.

넷째, wrapper/helper function 내부의 보안 검증을 정확히 해석하지 못하면 observed check를 누락할 수 있다.

다섯째, 복잡한 비동기 처리, callback, event-driven 구조에서는 source-sink flow confidence가 낮아질 수 있다.

따라서 F2-A는 모든 결과에 limitation을 명시해야 한다.

```
authorization policy evidence 모델링

wrapper/helper semantic summary 구축

```

## 21. 설계 원칙 요약

F2-A 상세 설계에서 유지해야 할 핵심 원칙은 다음과 같다.

```
1. F2-A는 취약점 확정기가 아니라 OCPP-native evidence extraction layer다.

2. F2-A는 F2-B의 입력 생성 전용 계층이 아니다.

3. F2-A와 F2-B는 F2-0 Common Code Fact Layer를 공유하는 독립 분석 계층이다.

4. F2-A는 OCPP action/field semantic을 source-code evidence와 연결한다.

5. Missing check는 단정이 아니라 candidate로 표현한다.

6. Runtime exploitability와 confirmed vulnerability는 F2-A가 판단하지 않는다.

7. F2-C는 F2-A 후보를 다시 OCPP_REACHABLE로 판정하지 않는다.

8. F2-C는 F2-B generic 후보의 external exposure를 분류한다.

9. F2-A의 모든 산출물은 file/function/line/evidence_id로 추적 가능해야 한다.

10. 초기 구현은 C 기반 controlled validation으로 시작하고, Java CSMS real-world applicability로 확장한다.
11. F2-A에서 선택적으로 사용하는 LLM은 취약점 탐지기가 아니라, observed check evidence가 F1 Expected Check Profile의 어떤 expected check에 대응하는지 분류하는 LLM-assisted Validation Checker로만 사용한다.
```

## 22. 결론

F2-A. OCPP-aware Static Analysis는 ChargeGuard-HVVD의 OCPP 도메인 특화 정적 분석 계층이다.

이 계층의 핵심 가치는 일반 정적 분석이 찾은 코드 흐름을 OCPP action/field의 보안 의미와 연결하는 데 있다. F2-A는 `location`, `idTag`, `connectorId`, `key`, `value`, `data`와 같은 payload field를 단순 입력값으로 보지 않고, OCPP 문맥에서 firmware download URL, authorization identifier, connector control parameter, configuration mutation parameter, custom data payload와 같은 보안 의미로 해석한다.

이를 통해 F2-A는 다음과 같은 OCPP-native evidence를 생성한다.

```
OCPP action/field
  → handler 또는 command path
  → field binding
  → source-sink / source-decision flow
  → observed check
  → missing expected check candidate
  → root cause candidate
  → related CWE
  → OCPP-native candidate HVVD fragment
```

F2-A의 출력은 취약점 확정 결과가 아니라 evidence-aware HVVD 생성을 위한 정적 근거 패키지이다. 따라서 F2-A는 ChargeGuard-HVVD 전체 구조에서 OCPP 도메인 지식과 소스코드 evidence를 연결하는 핵심 기반 계층으로 정의된다.

## 부록 A. 예시 코드

본 부록에서는 F2-A. OCPP-aware Static Analysis의 동작을 설명하기 위해 두 가지 예시를 사용한다.

첫 번째 예시는 C 기반 충전기 synthetic variant에서 `UpdateFirmware.location` 필드가 펌웨어 다운로드 URL로 사용되고, 검증 없이 shell command sink로 전달되는 사례이다.

두 번째 예시는 Java 기반 CSMS에서 `RemoteStartTransaction` 요청이 충분한 권한 및 상태 확인 없이 충전기 원격 시작 명령으로 전달되는 사례이다.

이 두 예시는 F2-A가 일반적인 취약점 탐지기가 아니라, OCPP action/field의 보안 의미를 코드 evidence와 연결하는 **OCPP-native evidence extraction layer**임을 보여주기 위한 것이다.

## A.1 C 기반 충전기 예시: UpdateFirmware.location

### A.1.1 예시 코드

```c
// file: dispatcher.c

#include <string.h>
#include "ocpp_handlers.h"

void dispatch_ocpp_action(const char* action, OcppRequest* req) {
    if (strcmp(action, "UpdateFirmware") == 0) {
        handle_update_firmware(req);
    } else if (strcmp(action, "ChangeConfiguration") == 0) {
        handle_change_configuration(req);
    }
}
```

```c
// file: firmware_update.c

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include "ocpp_handlers.h"

void handle_update_firmware(OcppRequest* req) {
    const char* firmware_url = req->location;

    if (firmware_url == NULL) {
        return;
    }

    download_firmware(firmware_url);
}

void download_firmware(const char* firmware_url) {
    char cmd[512];

    sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url);
    system(cmd);
}
```

### A.1.2 코드상 주요 흐름

```
OCPP action: UpdateFirmware
  → handler: handle_update_firmware(req)
  → field binding: req->location → firmware_url
  → function call: download_firmware(firmware_url)
  → command construction: sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url)
  → dangerous sink: system(cmd)
```

### A.1.3 F2-A 관점의 해석

이 코드는 일반 정적 분석 관점에서는 `system(cmd)` 호출과 외부 입력의 연결 여부를 중심으로 command injection 후보로 해석될 수 있다.

그러나 F2-A 관점에서는 분석 출발점이 다르다.

F2-A는 `system(cmd)`에서 출발하지 않고, OCPP action/field에서 출발한다.

```
UpdateFirmware.location
  → firmware_download_url
  → remote_ocpp_input
  → expected check 필요
  → source-sink flow 확인
  → observed check 확인
  → missing expected check candidate 생성
```

즉, `location`이라는 문자열 필드는 단순 문자열이 아니라, OCPP `UpdateFirmware` action의 펌웨어 다운로드 URL이라는 보안 의미를 가진 입력값으로 해석된다.

## A.2 Java CSMS Outbound 예시: RemoteStartTransaction

### A.2.1 예시 코드

```java
// file: RemoteStartCommandController.java

public class RemoteStartCommandController {

    private final RemoteStartCommandService remoteStartCommandService;

    public RemoteStartCommandController(RemoteStartCommandService remoteStartCommandService) {
        this.remoteStartCommandService = remoteStartCommandService;
    }

    public RemoteStartTransactionResponse remoteStart(RemoteStartCommandRequest request) {

```

```java
// file: RemoteStartCommandService.java

public class RemoteStartCommandService {

    private final ChargePointCommandService commandService;

    public RemoteStartCommandService(ChargePointCommandService commandService) {
        this.commandService = commandService;
    }

    public RemoteStartTransactionResponse start(RemoteStartCommandRequest request) {
        if (request.getIdTag() == null) {
            return RemoteStartTransactionResponse.rejected();
        }

        commandService.sendRemoteStartCommand(
            request.getChargePointId(),
            request.getConnectorId(),
            request.getIdTag()
        );

        return RemoteStartTransactionResponse.accepted();
    }
}
```

### A.2.2 코드상 주요 흐름

```
RemoteStartTransaction outbound command
  → command entry: RemoteStartCommandController.remoteStart()
  → field binding:
      request.getChargePointId()
      request.getConnectorId()
      request.getIdTag()
  → observed check:
      request.getIdTag() == null
  → service call:
      remoteStartCommandService.start(...)
  → command dispatch:
      commandService.sendRemoteStartCommand(...)
```

### A.2.3 F2-A 관점의 해석

이 예시는 command injection이나 memory corruption과 같은 전통적인 sink 중심 취약점과 다르다.

F2-A는 이 흐름을 OCPP-native authorization/state check missing 후보로 해석한다.

`RemoteStartTransaction`은 충전 세션을 원격으로 시작할 수 있는 action이므로, 단순 null check만으로 충분하지 않다. F1 Knowledge Layer는 이 action에 대해 다음 expected check를 정의할 수 있다.

```
operator permission check
station ownership check
idTag authorization check
connector availability check
station online state check
transaction state check
```

코드에서는 `idTag` null check만 관찰되므로, F2-A는 나머지 항목을 missing check candidate로 생성한다.

# 부록 B. F1. OCPP-centric Knowledge Layer 구축 예시

## B.1 F1 Knowledge Layer의 목적

F1. OCPP-centric Knowledge Layer는 F2-A가 OCPP action/field의 보안 의미를 코드 evidence와 연결할 수 있도록 기준 지식을 제공한다.

F1은 OCPP specification을 단순히 action 이름과 payload schema로 저장하는 계층이 아니다. F1은 각 action과 field가 보안상 어떤 의미를 가지며, 어떤 validation, authorization, state check, sink domain, root cause, impact, CWE 후보와 연결되는지를 구조화한다.

F2-A는 이 지식을 사용하여 다음과 같은 변환을 수행한다.

```
단순 field 이름
  → OCPP 보안 의미
  → expected check
  → dangerous sink domain
  → root cause candidate
  → related CWE
  → HVVD generation rule
```

예를 들어 `location`이라는 field 이름은 일반 코드에서는 단순 문자열로 보일 수 있다. 그러나 F1은 `UpdateFirmware.location`을 `firmware_download_url`로 정의함으로써, F2-A가 이를 펌웨어 다운로드 및 OTA 보안 문제와 연결할 수 있게 한다.

# 부록 E. F2-A 결과 해석 시 주의사항

## E.1 Missing check는 확정이 아니라 candidate이다

F2-A는 정적 분석 기반으로 observed check와 expected check를 비교한다. 그러나 정적 분석만으로는 모든 runtime policy, gateway-level authorization, deployment configuration, external policy server, framework interceptor를 완전히 확인할 수 없다.

따라서 F2-A의 missing check 결과는 다음과 같이 표현해야 한다.

```
missing_check_candidates
weak_check_candidates
unverified_check_candidates
```

다음과 같이 표현해서는 안 된다.

```
definitely vulnerable
confirmed missing check
runtime exploitable
```

## E.2 F2-A 결과는 OCPP-native candidate이다

F2-A는 OCPP action/field에서 출발하므로 그 결과는 OCPP-native candidate이다. 따라서 F2-C가 다시 F2-A 결과를 OCPP_REACHABLE로 판정할 필요는 없다.

F2-C는 F2-B에서 생성한 generic code vulnerability candidate가 어떤 외부 입력면을 통해 도달 가능한지를 분류하는 계층이다.

## E.3 F2-A와 F2-B의 병합은 F2-R에서 수행한다

동일한 코드 흐름은 F2-A와 F2-B에서 서로 다른 관점으로 분석될 수 있다.

예를 들어 `UpdateFirmware.location → system(cmd)` 흐름은 다음 두 후보로 생성될 수 있다.

```
F2-A:
  OCPP-native UpdateFirmware.location firmware URL validation missing candidate

F2-B:
  Generic command injection candidate
```

F2-R은 두 후보의 evidence를 병합하여 최종 candidate HVVD set을 구성한다.

# 부록 F. 부록 예제의 요약

본 부록의 예제는 F2-A의 역할을 다음과 같이 정리한다.

```
F1 Knowledge Layer:
  OCPP action/field의 보안 의미와 expected check를 정의한다.

F2-A Static Analysis:
    OCPP action/field를 코드의 handler 또는 command path, field binding,
    flow, sink/decision point, observed check와 연결한다.

F2-A Output:
  OCPP_NATIVE_CANDIDATE_HVVD_FRAGMENT와 evidence package를 생성한다.

F6 HVVD Generation:
  F2-A evidence를 기반으로 evidence-aware HVVD 후보를 생성한다.
```

핵심은 다음과 같다.

```
F2-A는 취약점 확정기가 아니다.
F2-A는 OCPP-native evidence extraction layer다.

F2-A는 F2-B의 입력 생성 전용 계층이 아니다.
F2-A와 F2-B는 F2-0 Common Code Fact Layer를 공유하는 독립 분석 계층이다.

F2-C는 F2-A 후보를 다시 OCPP_REACHABLE로 판정하지 않는다.
F2-C는 F2-B generic 후보의 external exposure를 분류한다.
```
