# F2-B. Type-specific LLM Vulnerability Candidate Classification

## 0. 개요

> 본 문서는 ChargeGuard-HVVD의 **F2-B Type-specific LLM Candidate Classification**에 대한 상세 개념 설계 문서이다.
> 

> 본 문서는 「ChargeGuard 기술 백서 v4」에서 정의한 F2-B의 상세 설계 문서이다.
> 

> ChargeGuard 기술 백서 v4는 F1~F7 전체 아키텍처와 책임 경계를 정의하며,
> 

> 본 문서는 그중 F2-B의 Detector Package, LLM_REQUEST, Detector Control Input, Analysis Target Evidence Input, Post-Processor, Candidate HVVD Mapping을 상세화한다.
> 

> 본 문서의 MVP 예시는 C 기반 충전기/Charge Point synthetic variant를 중심으로 Command Injection, Memory Safety, Firmware / OTA Weakness Detector Package를 설명한다.
> 

> 다만 F2-B의 핵심 구조는 특정 언어에 종속되지 않는다.
> 

> 향후 Java 기반 CSMS 분석으로 확장할 경우 Detector Package는 Backend Injection, Unsafe External Resource, Authorization & State Logic Weakness Detector Package로 재구성될 수 있으며, 공통 방법론은 Static Evidence → Detector Package → General-purpose LLM Engine → Structured Output → Post-Processor → Candidate HVVD 흐름을 유지한다.
> 

## 1. 개념 정의

**F2-B Type-specific LLM Vulnerability Candidate Classification**은 충전 인프라 소스코드에서 일반 보안 취약 후보를 분류하기 위해, 정적 분석으로 추출된 code evidence를 취약 유형별 Detector Package를 통해 General-purpose LLM Engine에 입력하고, 제한된 label space와 공통 output schema 안에서 `GENERIC_CODE_CANDIDATE_HVVD`를 생성하는 source-code-side 후보 분류 파이프라인이다.

이 단계는 하나의 범용 LLM이 전체 source code를 자유롭게 읽고 취약 여부를 단정하는 방식이 아니다. 먼저 F2-0 Common Code Fact Layer와 정적 분석 엔진이 함수, 호출 관계, source, sink, data-flow, observed check, missing check 후보를 추출한다. 이후 Detector Routing 단계에서 해당 evidence에 어떤 취약 유형별 Detector Package를 적용할지 결정하고, 선택된 Detector Package별로 Prompt와 LLM_CALL_INPUT을 포함한 LLM_REQUEST를 구성하여 General-purpose LLM Engine을 호출한다.

Detector Routing은 LLM이 수행하는 추론 단계가 아니라, 정적 분석 evidence, sink taxonomy, module context, security seed를 기반으로 수행되는 rule/static 기반 pre-routing 단계이다. LLM은 routing 이후 선택된 Detector Package가 구성한 LLM_REQUEST를 통해 candidate classification 단계에서만 사용된다.

LLM은 자유 서술문이 아니라 지정된 `TYPE_SPECIFIC_DETECTOR_OUTPUT` schema에 따라 JSON을 반환한다. 이후 Post-Processor는 LLM 출력의 schema, label, CWE, evidence consistency, forbidden claim 포함 여부를 검증하고, 검증된 결과를 `GENERIC_CODE_CANDIDATE_HVVD` fragment로 변환한다.

```
F2-B Type-specific LLM Vulnerability Candidate Classification
=
정적 분석 evidence를 기반으로
rule/static 기반 Detector Routing을 수행하고,
선택된 취약 유형별 Detector Package를 통해
General-purpose LLM Engine에 전달할 LLM_REQUEST를 구성하여
제한된 label space와 output schema 안에서
Generic Code Candidate HVVD를 생성하는
evidence-bounded 후보 분류 파이프라인
```

핵심 원칙은 다음과 같다.

```
F2-B는 LLM을 취약점 확정기로 사용하지 않는다.
F2-B는 Type-specific Detector Package를 통해 일반 LLM을
evidence-bounded candidate classifier로 제어한다.
```

따라서 F2-B에서 Detector Package에 의해 제어되는 General-purpose LLM Engine은 다음을 수행하지 않는다.

```
- 취약점 확정
- runtime exploit 가능성 단정
- OCPP 원격 exploit 가능성 단정
- evidence 없는 코드 경로 추측
- F5 validation 결과 대체
- CONFIRMED / DISMISSED 상태 자동 전이
```

F2-B의 산출물은 다음이다.

```
GENERIC_CODE_CANDIDATE_HVVD
```

단, F2-B 결과는 OCPP 원격 입력 경로와 연결되었다는 의미가 아니다. OCPP 노출 여부는 F2-C External Exposure Classification에서 별도로 분류한다.

F2-B는 F2-A의 후속 단계가 아니며, F2-A가 생성한 OCPP-native 후보를 재분류하는 계층도 아니다. F2-A와 F2-B는 모두 F2-0 Common Code Fact Layer를 공유하지만, 서로 다른 출발점과 분석 목적을 갖는 독립 분석 계층이다.

F2-A는 OCPP action/field에서 출발하여 handler, field binding, field semantic, source-flow-sink, observed check, expected check matching을 통해 OCPP-native Candidate HVVD Fragment를 생성한다.

반면 F2-B는 source-flow-sink evidence, sink evidence, function context, observed/missing check evidence에서 출발하여 Command Injection, Memory Safety, Firmware/OTA Weakness 등 취약 유형별 Generic Code Candidate HVVD Fragment를 생성한다.

F2-A에서 선택적으로 사용되는 LLM-assisted Validation Checker는 observed check evidence가 F1 Expected Check Profile의 어떤 expected check에 대응하는지 판정하는 check semantics classifier이다. 반면 F2-B의 LLM은 Type-specific Detector Package에 의해 제어되는 vulnerability candidate classifier이다.

## 2. 전체 Pipeline

F2-B Type-specific LLM Vulnerability Candidate Classification 의 전체 처리 흐름은 다음과 같다.

```
F2-0 Common Code Fact Layer
  ↓
Static Evidence Extraction
  ↓
Detector Routing
  ↓
Type-specific Detector Package 선택
  ├─ Command Injection Detector Package
  ├─ Memory Safety Detector Package
  └─ Firmware / OTA Weakness Detector Package
  ↓
LLM_REQUEST 구성
  ├─ Common Prompt
  └─ LLM_CALL_INPUT
      ├─ Detector Control Input
      └─ Analysis Target Evidence Input
  ↓
General-purpose LLM Engine 호출
  ↓
TYPE_SPECIFIC_DETECTOR_OUTPUT
  ↓
Detector-specific Post-Processor
  ├─ JSON Schema Validator
  ├─ Label Space Validator
  ├─ CWE Set Validator
  ├─ Evidence Consistency Checker
  ├─ Forbidden Claim Checker
  ├─ Confidence Adjuster
  ├─ Retry / Normalization Policy
  └─ Candidate HVVD Builder
  ↓
GENERIC_CODE_CANDIDATE_HVVD

```

요약하면 다음과 같다.

```
Static Evidence
→ Detector Routing
→ Type-specific Detector Package Selection
→ LLM_REQUEST 구성(Prompt + LLM_CALL_INPUT)
→ General-purpose LLM Engine 호출
→ TYPE_SPECIFIC_DETECTOR_OUTPUT
→ Post-Processor
→ GENERIC_CODE_CANDIDATE_HVVD

```

## 3. Detector Routing

Detector Routing은 정적 분석 evidence를 보고, 어떤 Type-specific Detector Package를 적용할지 결정하는 단계이다.

```
Detector Routing
=
정적 분석 evidence의 sink, API, data-flow, module context, security seed를 기반으로
적절한 취약 유형별 Detector Package를 선택하거나
복수 Detector Package에 분기시키는
rule/static 기반 pre-routing 단계
```

Detector Routing은 LLM 판단 결과가 아니다. 이 단계는 정적 분석 결과와 사전 정의된 routing rule을 사용하여 수행된다. LLM은 routing 이후 선택된 Detector Package가 구성한 LLM_REQUEST를 통해 candidate classification 단계에서만 사용된다.

라우팅이 필요한 이유는 다음과 같다.

```
- 모든 evidence를 모든 Detector에 넣으면 비용과 노이즈가 증가한다.
- 하나의 코드 조각이 여러 취약 유형에 해당할 수 있다.
- Detector별 label space와 판단 기준이 다르다.
- Detector별 Detector Control Input이 달라진다.
- 후처리 결과를 Candidate HVVD로 통합하려면 detector_type이 명확해야 한다.
```

Detector Routing은 다음 signal을 조합한다.

```
Detector Routing Signals
├─ Sink-based Signal
├─ API / Function Name Signal
├─ Data-flow Pattern Signal
├─ Module Context Signal
├─ Security Seed Signal
└─ Optional OCPP Context Signal
```

대표적인 라우팅 기준은 다음과 같다.

```
system(), popen(), Runtime.exec(), ProcessBuilder
  → Command Injection Detector Package

strcpy(), strcat(), sprintf(), memcpy(), array write
  → Memory Safety Detector Package

downloadFirmware(), installFirmware(), verifyFirmware(), updatePackage
  → Firmware / OTA Weakness Detector Package
```

data-flow 기준은 다음과 같다.

```
external_input → command_string → shell_execution
  → Command Injection Detector Package

external_input_length → copy_size → fixed_buffer
  → Memory Safety Detector Package

firmware_url → download → local_artifact → install
  → Firmware / OTA Weakness Detector Package
```

module context 기준은 다음과 같다.

```
firmware_update.c, ota_manager.c, update_installer.c
  → Firmware / OTA Weakness Detector Package

diagnostic_cmd.c, script_runner.c, shell_wrapper.c
  → Command Injection Detector Package

parser.c, buffer.c, packet_handler.c
  → Memory Safety Detector Package
```

라우팅은 단일 Detector만 선택하지 않아도 된다. 하나의 evidence가 여러 취약 유형에 걸칠 수 있기 때문이다.

예를 들어 다음 흐름은 복수 Detector로 라우팅될 수 있다.

```
firmware_url
  → sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url);
  → system(cmd)
  → install_firmware("/tmp/fw.bin")
```

라우팅 결과는 다음과 같다.

```
Command Injection Detector Package
  이유: 외부 입력이 command string에 결합되어 system()으로 전달됨

Memory Safety Detector Package
  이유: fixed-size buffer에 대해 sprintf() 기반 unbounded formatting pattern이 존재함

Firmware / OTA Weakness Detector Package
  이유: firmware URL에서 artifact를 다운로드하고 install_firmware()가 호출됨
```

즉, 이 예시는 단순 Command Injection 후보가 아니라, 동일 evidence가 여러 위험 관점으로 확장될 수 있는 multi-detector routing 사례이다.

라우팅 산출은 `DETECTOR_ROUTING_OUTPUT`으로 정의할 수 있다.

```
DETECTOR_ROUTING_OUTPUT
├─ target_id
├─ routing_mode
├─ selected_detectors
│  ├─ detector_type
│  ├─ routing_reason
│  ├─ routing_signal
│  └─ routing_confidence
├─ skipped_detectors
│  ├─ detector_type
│  └─ skip_reason
└─ routing_limitation
```

예시는 다음과 같다.

```json
{
  "target_id": "EVIDENCE-00042",
  "routing_mode": "MULTI_DETECTOR",
  "selected_detectors": [
    {
      "detector_type": "COMMAND_INJECTION",
      "routing_signal": [
        "sink_api: system",
        "data_flow: external_input_to_command_string"
      ],
      "routing_reason": "External input is inserted into a shell command and passed to system().",
      "routing_confidence": "HIGH"
    },
    {
      "detector_type": "MEMORY_SAFETY",
      "routing_signal": [
        "api: sprintf",
        "buffer_pattern: fixed_size_stack_buffer",
        "data_flow: external_input_to_unbounded_formatting"
      ],
      "routing_reason": "External input is formatted into a fixed-size buffer using sprintf().",
      "routing_confidence": "MEDIUM"
    },
    {
      "detector_type": "FIRMWARE_OTA",
      "routing_signal": [
        "module_context: firmware_update",
        "flow_pattern: firmware_url_to_download_to_install"
      ],
      "routing_reason": "The function downloads firmware from a URL and invokes firmware installation.",
      "routing_confidence": "MEDIUM"
    }
  ],
  "skipped_detectors": [],
  "routing_limitation": [
    "Routing is based on static evidence only.",
    "Detector routing does not imply vulnerability confirmation.",
    "External exposure, including OCPP reachability, is not classified at F2-B."
  ]
}
```

### 3.1 Type-specific Detector Package Selection

Detector Routing 이후에는 선택된 취약 유형에 맞는 `Type-specific Detector Package`를 적용한다. 여기서 Detector Package는 별도의 LLM 모델을 의미하지 않는다. 이는 일반 LLM 엔진을 특정 취약 유형의 후보 분류기로 동작시키기 위해 필요한 입력 필터, 판단 규칙, label space, CWE set, 출력 schema, 후처리 규칙을 묶은 제어 패키지이다.

```
Type-specific Detector Package
=
General-purpose LLM Engine에 전달할 LLM_REQUEST를 구성하기 위한
취약 유형별 제어 패키지
```

Detector Routing은 정적 분석 evidence를 기반으로 어떤 Detector Package를 사용할지 결정한다. 예를 들어 `system()`, `popen()`, `Runtime.exec()`와 같은 shell execution sink가 관찰되면 `Command Injection Detector Package`가 선택된다. 고정 크기 버퍼와 `sprintf()`, `strcpy()`, `memcpy()`와 같은 위험 write pattern이 관찰되면 `Memory Safety Detector Package`가 선택될 수 있다. firmware download, verification, install flow가 관찰되면 `Firmware / OTA Weakness Detector Package`가 선택될 수 있다.

선택된 Detector Package는 이후 `LLM_REQUEST`의 내용을 구성하는 데 사용된다.

```
Detector Routing
  ↓
Type-specific Detector Package 선택
  ↓
LLM_REQUEST 구성
  ├─ Common Prompt
  └─ LLM_CALL_INPUT
      ├─ Detector Control Input
      │   ├─ detector_type
      │   ├─ allowed_label_space
      │   ├─ allowed_cwe_set
      │   ├─ detector_specific_rules
      │   ├─ forbidden_claims
      │   └─ required_output_schema
      └─ Analysis Target Evidence Input
          └─ Detector Package 기준에 따라 필요한 evidence만 필터링
```

따라서 `Type-specific Detector Package 선택`은 General-purpose LLM Engine을 호출하기 전, 해당 LLM 호출이 어떤 취약 유형 관점에서 수행될지 결정하고 `LLM_REQUEST`를 채우는 단계이다. 이 구조를 통해 F2-B는 전용 LLM 모델을 별도로 학습하지 않고도, 일반 LLM을 Command Injection, Memory Safety, Firmware / OTA Weakness 등 취약 유형별 candidate classifier로 제어할 수 있다.

## 4. LLM_REQUEST 구성

Detector Routing 이후, 선택된 Detector Package별로 별도의 LLM 호출 요청을 구성한다.

F2-B의 LLM 요청은 다음과 같이 구성된다.

```
LLM_REQUEST
├─ Prompt
└─ LLM_CALL_INPUT
   ├─ Detector Control Input
   └─ Analysis Target Evidence Input
```

각 구성요소의 역할은 다음과 같다.

```
Prompt
=
General-purpose LLM Engine이 어떻게 행동하고 판단해야 하는지를 지시하는 공통 실행 규칙

Detector Control Input
=
이번 호출에서 어떤 detector_type과 Detector Package 관점을 적용할지,
어떤 label과 CWE 범위를 허용할지,
어떤 output schema로 응답해야 하는지를 정의하는 호출별 제어 입력

Analysis Target Evidence Input
=
LLM이 실제로 보고 판단해야 하는 정적 분석 evidence package
```

선택된 Detector Package가 복수이면 Detector Package별로 별도의 `LLM_REQUEST`를 생성한다.

```
Detector Routing 결과:
  selected_detectors = [
    COMMAND_INJECTION,
    MEMORY_SAFETY,
    FIRMWARE_OTA
  ]

LLM_REQUEST Builder:
  ├─ COMMAND_INJECTION용 LLM_REQUEST 생성
  ├─ MEMORY_SAFETY용 LLM_REQUEST 생성
  └─ FIRMWARE_OTA용 LLM_REQUEST 생성
```

같은 evidence라도 Detector별 `Detector Control Input`은 달라진다. 또한 `Analysis Target Evidence Input`은 동일 원본 evidence를 공유하되, Detector별 판단에 필요한 부분만 필터링하거나 강조할 수 있다.

## 5. Prompt 설계

Prompt는 F2-B에서 General-purpose LLM Engine을 Type-specific Detector Package의 제어 범위 안에서 동작시키기 위한 공통 LLM 행동 규칙이다.

```
Prompt
=
General-purpose LLM Engine이 어떤 역할로 행동해야 하는지,
어떤 evidence만 사용해야 하는지,
무엇을 단정하면 안 되는지,
어떤 label space와 output schema 안에서 응답해야 하는지를 지시하는
공통 실행 지시문
```

Prompt는 다음 요소로 구성한다.

```
Prompt
├─ role_instruction
├─ task_instruction
├─ evidence_usage_rule
├─ label_selection_rule
├─ forbidden_claim_rule
└─ output_format_rule
```

공통 Prompt 예시는 다음과 같다.

```
You are a type-specific vulnerability candidate classifier.
You are not a vulnerability confirmer.

Your detector type is defined in LLM_CALL_INPUT.Detector_Control_Input.

Use only the provided static analysis evidence.
Do not infer runtime exploitability.
Do not infer OCPP reachability.
Do not claim the issue is confirmed.
Do not invent unobserved source-to-sink flows.

Classify the evidence using only the allowed label space provided in Detector Control Input.
If the evidence is incomplete, select the most appropriate label from the allowed_label_space, preferably the detector-specific POSSIBLE label or UNKNOWN, and explain the limitation.

Return only a valid JSON object that conforms to the required_output_schema specified in Detector Control Input.
Do not include markdown, commentary, or explanatory text outside the JSON object.
```

Prompt의 핵심 효과는 다음과 같다.

```
- LLM을 candidate classifier 역할로 제한
- 제공된 evidence 외 추론 금지
- allowed label space 사용 강제
- forbidden claim 방지
- JSON schema 기반 출력 유도
```

## 6. Detector Control Input 설계

Detector Control Input은 `LLM_CALL_INPUT`의 일부이며, 이번 LLM 호출에서 적용할 Detector별 설정값을 정의한다.

```
Detector Control Input
=
이번 LLM 호출에서 어떤 detector_type과 Detector Package 관점을 적용할지,
어떤 label space를 사용할지,
어떤 CWE 후보를 허용할지,
어떤 판단 규칙을 적용할지,
어떤 출력 schema를 요구할지 정의하는 제어 입력
```

구성은 다음과 같다.

```
Detector Control Input
├─ detector_type
├─ detector_objective
├─ allowed_label_space
├─ allowed_cwe_set
├─ detector_specific_rules
├─ evidence_usage_policy
├─ forbidden_claims
└─ required_output_schema
```

각 항목의 의도는 다음과 같다.

| 항목 | 의도 |
| --- | --- |
| `detector_type` | 이번 LLM 호출에서 적용할 취약 유형 관점을 지정한다. LLM이 어떤 취약 유형 관점에서 evidence를 판단해야 하는지 고정한다. |
| `detector_objective` | 해당 detector_type 관점에서 이번 evidence에 대해 무엇을 판정해야 하는지 설명한다. “취약점 확정”이 아니라 “candidate 여부 분류”를 목표로 해야 한다. |
| `allowed_label_space` | LLM이 선택할 수 있는 classification label 범위를 제한한다. 자유로운 취약 판단 표현 대신 후처리 가능한 label 중 하나만 선택하게 한다. |
| `allowed_cwe_set` | 해당 detector_type에서 제시할 수 있는 CWE 후보 범위를 제한한다. evidence와 무관한 CWE 확장을 방지한다. |
| `detector_specific_rules` | Analysis Target Evidence Input을 해석하여 allowed_label_space 중 하나의 classification_label로 분류하기 위한 Detector별 판정 기준이다. |
| `evidence_usage_policy` | LLM이 제공된 evidence만 사용하도록 제한하고, 관찰되지 않은 flow, runtime exploitability, OCPP reachability 등을 추론하지 못하게 한다. |
| `forbidden_claims` | LLM 출력에 포함되면 안 되는 금지 주장 또는 금지 표현을 정의한다. Post-Processor가 이를 검출한다. |
| `required_output_schema` | LLM이 반환해야 하는 JSON schema를 지정한다. 자유 서술문이 아니라 시스템이 파싱 가능한 구조화 출력으로 제한한다. |

정리하면, Detector Control Input은 LLM의 판단을 다음 네 가지 측면에서 통제한다.

```
1. 판단 관점 통제:
   detector_type, detector_objective

2. 판정 범위 통제:
   allowed_label_space, allowed_cwe_set

3. 추론 방식 통제:
   detector_specific_rules, evidence_usage_policy, forbidden_claims

4. 출력 형식 통제:
   required_output_schema
```

## 7. Analysis Target Evidence Input 설계

Analysis Target Evidence Input은 LLM이 실제로 보고 판단해야 하는 정적 분석 evidence package이다.

```
Analysis Target Evidence Input
=
정적 분석으로 추출된 source, sink, data-flow, observed check,
missing check 후보, code slice, call chain을 담은 판단 대상 입력
```

구성은 다음과 같다.

```
Analysis Target Evidence Input
├─ target_metadata
├─ function_summary
├─ relevant_code_slice
├─ source_candidate
├─ sink_candidate
├─ data_flow_evidence
├─ call_chain_evidence
├─ observed_checks
├─ missing_or_weak_check_candidates
├─ wrapper_or_helper_summary
├─ generic_security_seed
└─ optional_ocpp_context
```

각 항목의 의도는 다음과 같다.

| 항목 | 의도 |
| --- | --- |
| `target_metadata` | 분석 대상 파일, 함수, 언어, line range, target ID를 지정한다. |
| `function_summary` | 대상 함수의 역할과 모듈 맥락을 제공한다. |
| `relevant_code_slice` | LLM이 판단할 최소 코드 조각을 제공한다. 전체 원시코드가 아니라 정적 분석으로 축약된 관련 코드만 포함한다. |
| `source_candidate` | 외부 입력, 설정값, 네트워크 입력, function parameter 등 source 후보를 정의한다. |
| `sink_candidate` | system(), popen(), strcpy(), installFirmware() 등 위험 sink 후보를 정의한다. |
| `data_flow_evidence` | source에서 sink까지 값이 어떻게 전달되는지 단계별 evidence를 제공한다. |
| `call_chain_evidence` | 함수 간 호출 경로 evidence를 제공한다. |
| `observed_checks` | 코드에서 관찰된 방어 check를 제공한다. |
| `missing_or_weak_check_candidates` | 기대되는 check 중 누락되었거나 약한 check 후보를 제공한다. |
| `wrapper_or_helper_summary` | wrapper/helper 함수 내부 동작 요약을 제공한다. |
| `generic_security_seed` | 정적 분석 또는 KB가 부여한 일반 보안 seed를 제공한다. |
| `optional_ocpp_context` | 이미 알려진 OCPP action/field hint를 보조 정보로 제공할 수 있다. 단, F2-B는 이를 근거로 OCPP reachability를 판정하지 않는다. |

`optional_ocpp_context`는 신중하게 사용해야 한다. 

F2-B의 General-purpose LLM Engine은 이 필드를 근거로 OCPP_REACHABLE, EXTERNAL_EXPOSED, remote exploitability, protocol behavior anomaly를 판단해서는 안 된다.

외부 입력면 연결성은 F2-C External Exposure Classification에서 별도로 분류한다.

## 8. General-purpose LLM Engine 호출: Type-specific Detector Package 실행

F2-B는 취약 유형별 전용 LLM 모델을 별도로 학습하거나 구축하는 방식이 아니다. 대신 일반 LLM 엔진을 공통 추론 백엔드로 활용하되, 취약 유형별 `Detector Package`를 통해 LLM 호출 방식을 제어한다.

즉, F2-B에서 개발해야 하는 것은 Command Injection 전용 LLM, Memory Safety 전용 LLM, Firmware / OTA 전용 LLM이 아니다. 실제 개발 대상은 각 취약 유형에 맞는 evidence filter, detector control input, label space, CWE set, detector-specific rules, output schema, post-processing rule, HVVD mapping rule을 포함하는 `Type-specific Detector Package`이다.

```
General-purpose LLM Engine
=
일반 LLM 추론 백엔드
예: 상용 LLM API, 오픈소스 LLM, 폐쇄망 LLM, vLLM 기반 serving 등

Type-specific Detector Package
=
일반 LLM을 특정 취약 유형의 후보 분류기로 동작시키기 위한
입력·규칙·출력·검증 제어 패키지
```

MVP에서는 다음 3개 Detector Package를 기본으로 둔다.

```
MVP F2-B Detector Packages
├─ Command Injection Detector Package
├─ Memory Safety Detector Package
└─ Firmware / OTA Weakness Detector Package
```

각 Detector Package는 동일한 `LLM_REQUEST` 구조를 사용하지만, 서로 다른 `Detector Control Input`, `allowed_label_space`, `allowed_cwe_set`, `detector_specific_rules`, `post-processing rule`을 갖는다.

```
LLM_REQUEST
├─ Common Prompt
└─ LLM_CALL_INPUT
   ├─ Detector Control Input
   └─ Analysis Target Evidence Input
```

여기서 `Analysis Target Evidence Input`은 LLM이 실제로 판단해야 하는 정적 분석 근거이고, `Detector Control Input`은 해당 근거를 어떤 취약 유형 관점에서 어떻게 분류할지를 정의하는 제어 입력이다.

특히 `detector_specific_rules`는 `Analysis Target Evidence Input`에 포함된 source, sink, data-flow, observed check, missing check 근거를 해석하여 `allowed_label_space` 중 하나의 `classification_label`로 분류하기 위한 Detector별 판정 기준이다.

```
Analysis Target Evidence Input
= 판단 대상 근거

allowed_label_space
= 선택 가능한 label 목록

detector_specific_rules
= 어떤 evidence 조합이면 어떤 label을 선택할지 정하는 Detector별 판정 기준
```

따라서 Type-specific Detector Package의 실행 흐름은 다음과 같다.

```
1. Detector Routing 결과에 따라 실행할 Detector Package를 선택한다.
2. 선택된 Detector Package가 필요한 evidence만 필터링한다.
3. Detector Control Input을 구성한다.
4. Common Prompt와 LLM_CALL_INPUT을 결합하여 LLM_REQUEST를 생성한다.
5. General-purpose LLM Engine을 호출한다.
6. LLM은 detector_specific_rules에 따라 evidence를 해석한다.
7. allowed_label_space 중 하나를 classification_label로 선택한다.
8. 선택한 label의 근거를 evidence_basis에 기록한다.
9. 판단 한계는 limitation에 기록한다.
10. TYPE_SPECIFIC_DETECTOR_OUTPUT schema에 맞는 JSON을 반환한다.
11. Detector-specific Post-Processor가 출력의 schema, label, CWE, evidence consistency, forbidden claim을 검증한다.
```

중요한 점은 `detector_specific_rules`가 직접 분류를 수행하는 코드가 아니라는 것이다. 실제 분류는 General-purpose LLM Engine이 수행한다. 다만 LLM은 Detector Package가 제공한 evidence, label space, CWE set, detector-specific rules, forbidden claim rule, required output schema의 범위 안에서만 판단해야 한다.

```
Static Evidence
  ↓
Detector Routing
  ↓
Type-specific Detector Package 선택
  ↓
Evidence Filtering + Detector Control Input 구성
  ↓
General-purpose LLM Engine 호출
  ↓
detector_specific_rules에 따른 LLM 해석
  ↓
allowed_label_space 중 classification_label 선택
  ↓
TYPE_SPECIFIC_DETECTOR_OUTPUT 생성
  ↓
Detector-specific Post-Processor 검증
```

이 구조에서 LLM은 취약점 확정기가 아니라, Detector Package에 의해 제어되는 evidence-bounded candidate classifier로 동작한다.

### 8.1 Command Injection Detector Package

Command Injection Detector Package는 외부 입력이 shell command, script execution, process execution API로 전달되는 정적 근거를 분석하기 위해 General-purpose LLM Engine을 제어하는 패키지이다.

```
Command Injection Detector Package
=
외부 입력이 command string 또는 shell execution sink로 전달되는지,
그리고 shell-free execution, argument allowlist, metacharacter neutralization 등
의미 있는 방어 근거가 존재하는지를
일반 LLM이 evidence 기반으로 분류하도록 제어하는 Detector Package
```

이 Package는 다음 요소를 포함한다.

```
Command Injection Detector Package
├─ command execution sink taxonomy
├─ command-related evidence filter
├─ Detector Control Input
├─ allowed_label_space
├─ allowed_cwe_set
├─ detector_specific_rules
├─ forbidden_claims
├─ TYPE_SPECIFIC_DETECTOR_OUTPUT schema
├─ post-processing rule
└─ HVVD mapping rule
```

대상 sink는 다음과 같다.

```
C/C++:
  - system()
  - popen()
  - execl()
  - execv()
  - execve()
  - fork + exec
  - shell script invocation

Java:
  - Runtime.exec()
  - ProcessBuilder
  - shell wrapper execution
```

label space는 다음과 같다.

```
COMMAND_INJECTION_LIKELY
COMMAND_INJECTION_POSSIBLE
COMMAND_INJECTION_GUARDED
NO_COMMAND_INJECTION_EVIDENCE
UNKNOWN
```

Command Injection Detector Package의 `detector_specific_rules`는 다음 기준으로 evidence를 해석하게 한다.

```
COMMAND_INJECTION_LIKELY:
  external input source가 존재하고,
  해당 source가 command string에 concat, format, interpolation 방식으로 결합되며,
  command string이 system(), popen(), Runtime.exec(), ProcessBuilder 또는 동등한 shell execution sink로 전달되고,
  shell-free execution, argument allowlist, shell metacharacter neutralization, safe wrapper enforce 등의 의미 있는 방어 근거가 없는 경우 선택한다.

COMMAND_INJECTION_POSSIBLE:
  source-to-sink flow가 부분적으로만 확인되거나,
  source의 trust level이 불명확하거나,
  command execution sink는 있으나 외부 입력이 command string에 도달하는 근거가 불완전하거나,
  방어 check 존재 여부가 불완전한 경우 선택한다.

COMMAND_INJECTION_GUARDED:
  command execution sink는 존재하지만,
  shell-free argument array execution, allowlist, shell metacharacter neutralization,
  safe wrapper enforced command boundary 등 의미 있는 방어 근거가 관찰되는 경우 선택한다.

NO_COMMAND_INJECTION_EVIDENCE:
  command execution sink가 없거나,
  command execution sink는 있으나 외부 입력이 해당 sink로 전달되는 근거가 없는 경우 선택한다.

UNKNOWN:
  evidence가 부족하여 source, sink, flow, guard 여부를 판단할 수 없는 경우 선택한다.
```

`COMMAND_INJECTION_GUARDED`는 안전 확정을 의미하지 않는다. 이는 command injection 위험 pattern에 대해 의미 있는 방어 근거가 관찰되었다는 뜻이며, 방어의 충분성은 후속 검토 또는 별도 검증에서 추가 확인될 수 있다.

### 8.2 Memory Safety Detector Package

Memory Safety Detector Package는 C/C++ 코드에서 buffer overflow, out-of-bounds write, unsafe copy, format string, size mismatch 후보를 분류하기 위해 General-purpose LLM Engine을 제어하는 패키지이다.

```
Memory Safety Detector Package
=
고정 크기 버퍼, 포인터, 배열, copy length, format string 사용과 관련된
정적 evidence를 일반 LLM이 memory safety 관점에서 해석하도록 제어하는 Detector Package
```

이 Package는 다음 요소를 포함한다.

```
Memory Safety Detector Package
├─ memory safety sink taxonomy
├─ buffer / length / write evidence filter
├─ Detector Control Input
├─ allowed_label_space
├─ allowed_cwe_set
├─ detector_specific_rules
├─ forbidden_claims
├─ TYPE_SPECIFIC_DETECTOR_OUTPUT schema
├─ post-processing rule
└─ HVVD mapping rule
```

대상 sink는 다음과 같다.

```
C/C++:
  - strcpy
  - strcat
  - sprintf
  - vsprintf
  - memcpy
  - memmove
  - scanf family
  - array index write
  - pointer arithmetic write
  - fixed-size buffer copy
  - externally controlled format string
```

label space는 다음과 같다.

```
MEMORY_SAFETY_LIKELY
MEMORY_SAFETY_POSSIBLE
MEMORY_SAFETY_GUARDED
NO_MEMORY_SAFETY_EVIDENCE
UNKNOWN
```

Memory Safety Detector Package의 `detector_specific_rules`는 다음 기준으로 evidence를 해석하게 한다.

```
MEMORY_SAFETY_LIKELY:
  fixed-size buffer, array, heap buffer, pointer destination 중 하나가 존재하고,
  외부 입력 또는 untrusted length가 copy/write/index/format operation에 사용되며,
  destination capacity 또는 index bound에 대한 검증 근거가 없고,
  unbounded copy, unchecked sprintf, out-of-bounds write, externally controlled format string 등 위험 sink가 관찰되는 경우 선택한다.

MEMORY_SAFETY_POSSIBLE:
  위험 API 또는 위험 write pattern은 있으나 buffer size나 input length 근거가 불완전하거나,
  source trust level이 불명확하거나,
  capacity check가 있는지 불분명하거나,
  wrapper 내부 동작이 확인되지 않는 경우 선택한다.

MEMORY_SAFETY_GUARDED:
  위험 API 또는 copy/write operation은 존재하지만,
  capacity check, bounded copy, index bounds check, null termination 보장,
  fixed format string 등 의미 있는 방어 근거가 관찰되는 경우 선택한다.

NO_MEMORY_SAFETY_EVIDENCE:
  memory safety 관련 sink 또는 위험 write pattern이 관찰되지 않는 경우 선택한다.

UNKNOWN:
  evidence가 부족하여 buffer size, source length, copy size, bounds check 여부를 판단할 수 없는 경우 선택한다.
```

`MEMORY_SAFETY_GUARDED`는 안전 확정을 의미하지 않는다. 이는 memory safety 위험 pattern에 대해 의미 있는 방어 근거가 관찰되었다는 뜻이며, guard의 충분성은 후속 검토에서 추가 확인될 수 있다.

### 8.3 Firmware / OTA Weakness Detector Package

Firmware / OTA Weakness Detector Package는 firmware download, artifact verification, installation guard, rollback 방지, update script execution과 관련된 보안 취약 후보를 분류하기 위해 General-purpose LLM Engine을 제어하는 패키지이다.

```
Firmware / OTA Weakness Detector Package
=
firmware artifact가 신뢰 가능한 출처에서 내려받아지고,
무결성·서명·버전·설치 차단 조건을 충족한 뒤 설치되는지
일반 LLM이 firmware update 보안 관점에서 해석하도록 제어하는 Detector Package
```

이 Package는 다음 요소를 포함한다.

```
Firmware / OTA Weakness Detector Package
├─ firmware update evidence filter
├─ firmware / OTA security rule set
├─ Detector Control Input
├─ allowed_label_space
├─ allowed_cwe_set
├─ detector_specific_rules
├─ forbidden_claims
├─ TYPE_SPECIFIC_DETECTOR_OUTPUT schema
├─ post-processing rule
└─ HVVD mapping rule
```

대상 코드 영역은 다음과 같다.

```
- firmware download function
- update package parser
- installFirmware()
- verifyFirmware()
- checksum / hash verification
- digital signature verification
- rollback version check
- reboot / reset after update
- update script execution
- firmware temporary file handling
```

label space는 다음과 같다.

```
FIRMWARE_OTA_WEAKNESS_LIKELY
FIRMWARE_OTA_WEAKNESS_POSSIBLE
FIRMWARE_OTA_GUARDED
NO_FIRMWARE_OTA_EVIDENCE
UNKNOWN
```

Firmware / OTA Weakness Detector Package의 `detector_specific_rules`는 다음 기준으로 evidence를 해석하게 한다.

```
FIRMWARE_OTA_WEAKNESS_LIKELY:
  firmware download 또는 firmware install flow가 존재하고,
  외부 URL, remote artifact, update package, local firmware file이 install flow로 이어지며,
  signature verification, hash verification, trusted source check,
  install-block-on-verify-fail 근거가 없는 경우 선택한다.

FIRMWARE_OTA_WEAKNESS_POSSIBLE:
  firmware update flow는 있으나 download와 install 사이의 검증 근거가 불완전하거나,
  verify 함수가 존재하지만 install block과 연결되는지 불명확하거나,
  hash check는 있으나 signature/authenticity 검증 여부가 불명확하거나,
  rollback version check 여부가 불완전한 경우 선택한다.

FIRMWARE_OTA_GUARDED:
  firmware update flow가 존재하지만,
  trusted source 또는 host allowlist,
  firmware signature verification,
  hash 또는 integrity verification,
  verification 실패 시 install 차단,
  rollback version check,
  update artifact 저장 경로 제한 등 의미 있는 방어 근거가 관찰되는 경우 선택한다.

NO_FIRMWARE_OTA_EVIDENCE:
  firmware/OTA download, verification, install 관련 근거가 없는 경우 선택한다.

UNKNOWN:
  evidence가 부족하여 firmware update flow 또는 검증·설치 차단 여부를 판단할 수 없는 경우 선택한다.
```

`FIRMWARE_OTA_GUARDED`는 안전 확정을 의미하지 않는다. 이는 firmware/OTA 위험 pattern에 대해 의미 있는 방어 근거가 관찰되었다는 뜻이며, 방어의 충분성은 후속 검토 또는 protocol-behavior validation에서 추가 확인될 수 있다.

### 8.4 Detector Package 실행 결과의 의미

Type-specific Detector Package를 통해 General-purpose LLM Engine이 반환한 `classification_label`은 최종 취약점 판정이 아니다. 이는 제공된 정적 분석 evidence와 Detector별 판정 규칙에 근거한 후보 분류 결과이다.

```
classification_label
=
Analysis Target Evidence Input을
detector_specific_rules에 따라 해석한 뒤
allowed_label_space 중 하나로 선택한 후보 분류 결과
```

따라서 다음과 같이 해석해야 한다.

```
LIKELY:
  정적 evidence 기준으로 해당 취약 유형의 후보 가능성이 높음

POSSIBLE:
  일부 근거가 있으나 flow, source trust, guard 여부가 불완전함

GUARDED:
  위험 pattern은 있으나 의미 있는 방어 근거가 관찰됨

NO_EVIDENCE:
  해당 취약 유형에 대한 근거가 없음

UNKNOWN:
  evidence가 부족해 판단 불가능함
```

이 결과는 다음을 의미하지 않는다.

```
- 취약점 확정 아님
- runtime exploitability 확인 아님
- OCPP remote exploitability 확인 아님
- F5 validation 결과 아님
- CONFIRMED_HVVD 상태 전이 아님
```

정리하면, F2-B의 classification_label은 Detector Package가 제공한 evidence, label space, detector_specific_rules에 따라 General-purpose LLM Engine이 선택한 후보 분류 결과이다. 이는 최종 취약점 판정이 아니며, 후속 Post-Processor와 F2-C/F6 단계에서 추가 검증·보강된다.

Detector Package별 차이는 Detector Control Input, allowed_label_space, allowed_cwe_set, detector_specific_rules에서 정의되며, `classification_label`은 이 제어 범위 안에서만 선택된다.

특히 `detector_specific_rules`는 `Analysis Target Evidence Input`에 포함된 source, sink, data-flow, observed check, missing check 근거를 해석하여 `allowed_label_space` 중 하나의 `classification_label`로 분류하기 위한 Detector별 판정 기준이다.

```
Analysis Target Evidence Input
= 판단 대상 근거

allowed_label_space
= 선택 가능한 label 목록

detector_specific_rules
= 어떤 evidence 조합이면 어떤 label을 선택할지 정하는 Detector별 판정 기준
```

Type-specific Detector Package 기반 LLM 후보 분류의 실행 흐름은 다음과 같다.

```
1. Analysis Target Evidence Input을 읽는다.
2. Detector Control Input의 detector_type을 확인한다.
3. detector_specific_rules에 따라 evidence를 해석한다.
4. allowed_label_space 중 하나를 classification_label로 선택한다.
5. 선택한 label의 근거를 evidence_basis에 기록한다.
6. 판단 한계는 limitation에 기록한다.
7. TYPE_SPECIFIC_DETECTOR_OUTPUT schema에 맞는 JSON을 반환한다.
```

중요한 점은 `detector_specific_rules`가 직접 분류를 수행하는 코드가 아니라는 것이다. 실제 분류는 LLM이 수행한다. 다만 LLM은 `detector_specific_rules`를 따라야 하며, 이후 Post-Processor는 LLM이 선택한 `classification_label`이 입력 evidence, allowed label space, allowed CWE set, forbidden claim rule과 일관되는지 검증한다.

```
Analysis Target Evidence Input
  ↓
detector_specific_rules에 따른 LLM 해석
  ↓
allowed_label_space 중 classification_label 선택
  ↓
TYPE_SPECIFIC_DETECTOR_OUTPUT 생성
  ↓
Post-Processor 검증
```

## 9. TYPE_SPECIFIC_DETECTOR_OUTPUT

General-purpose LLM Engine은 선택된 Detector Package의 제어를 받아 자유 서술문이 아니라 `TYPE_SPECIFIC_DETECTOR_OUTPUT`  schema에 맞는 JSON만 반환한다.

공통 schema는 다음과 같다.

```
TYPE_SPECIFIC_DETECTOR_OUTPUT
├─ detector_type
├─ classification_label
├─ vulnerability_class
├─ source_summary
├─ sink_summary
├─ flow_summary
├─ observed_checks
├─ missing_or_weak_checks
├─ root_cause_candidate
├─ related_cwe
├─ evidence_basis
├─ confidence
├─ limitation
└─ recommended_hvvd_type
```

`classification_label`은 반드시 해당 Detector의 `allowed_label_space` 안에 있어야 한다. `related_cwe` 역시 해당 Detector의 `allowed_cwe_set` 안에 있어야 한다.

예를 들어 detector_type이 COMMAND_INJECTION인 경우 출력은 다음과 같다.

```json
{
  "detector_type": "COMMAND_INJECTION",
  "classification_label": "COMMAND_INJECTION_LIKELY",
  "vulnerability_class": "command_injection",
  "source_summary": {
    "source": "firmware_url",
    "source_type": "external_input",
    "origin": "function_parameter",
    "trust_level": "untrusted_or_unknown"
  },
  "sink_summary": {
    "sink": "system(cmd)",
    "sink_type": "shell_command_execution",
    "sink_api": "system",
    "evidence_id": "SINK-00042"
  },
  "flow_summary": {
    "flow_observed": true,
    "summary": "The firmware_url value is formatted into a shell command string through sprintf and the resulting command buffer is passed to system()."
  },
  "observed_checks": [
    {
      "check": "NULL_CHECK",
      "evidence_id": "CHECK-00042",
      "assessment": "This check only verifies nullness and does not constrain command content or shell metacharacters."
    }
  ],
  "missing_or_weak_checks": [
    {
      "check": "SHELL_FREE_EXECUTION",
      "evidence_id": "MCHECK-00017"
    },
    {
      "check": "COMMAND_ARG_ALLOWLIST",
      "evidence_id": "MCHECK-00018"
    },
    {
      "check": "SHELL_METACHARACTER_ESCAPE",
      "evidence_id": "MCHECK-00019"
    }
  ],
  "root_cause_candidate": "external_input_to_shell_command_without_safe_argument_boundary",
  "related_cwe": [
    "CWE-78"
  ],
  "evidence_basis": [
    {
      "type": "source",
      "evidence_id": "SRC-00042",
      "detail": "firmware_url is identified as an external input function parameter."
    },
    {
      "type": "source_to_sink_flow",

      "type": "source_to_sink_flow",

```

`COMMAND_INJECTION_LIKELY`는 정적 evidence 기준으로 command injection 후보 가능성이 높다는 의미이며, runtime exploitability 또는 OCPP remote exploitability를 의미하지 않는다.

## 10. Post-Processor

Post-Processor는 LLM의 `TYPE_SPECIFIC_DETECTOR_OUTPUT`을 검증하고, 검증된 결과를 `GENERIC_CODE_CANDIDATE_HVVD` fragment로 변환하는 계층이다.

```
TYPE_SPECIFIC_DETECTOR_OUTPUT
  ↓
Post-Processor
  ├─ JSON Schema Validator
  ├─ Label Space Validator
  ├─ CWE Set Validator
  ├─ Evidence Consistency Checker
  ├─ Forbidden Claim Checker
  ├─ Confidence Adjuster
  ├─ Retry / Normalization Policy
  └─ Candidate HVVD Builder
  ↓
GENERIC_CODE_CANDIDATE_HVVD
```

Post-Processor는 다음 항목을 검증한다.

```
- 출력이 required_output_schema를 만족하는가?
- detector_type이 호출된 Detector Package의 detector_type과 일치하는가?
- classification_label이 allowed_label_space 안에 있는가?
- related_cwe가 allowed_cwe_set 안에 있는가?
- evidence_basis가 입력 evidence를 참조하는가?
- forbidden claim이 포함되어 있지 않은가?
- confidence와 limitation이 누락되지 않았는가?
```

예외 처리 기준은 다음과 같이 둔다.

```
Schema violation:
  retry_with_strict_json_prompt 또는 reject

Invalid label:
  retry 또는 normalize_to_UNKNOWN

Unsupported CWE:
  remove unsupported CWE 또는 mark unsupported_cwe

Missing evidence_basis:
  retry 또는 lower confidence

Forbidden claim detected:
  reject 또는 retry_with_forbidden_claim_reminder

Missing limitation:
  add default limitation 또는 retry

Evidence inconsistency:
  lower confidence, flag evidence_mismatch, 또는 reject
```

Post-Processor의 핵심 목적은 LLM 출력의 자유도를 다시 한 번 통제하여, F2-B 결과가 시스템적으로 신뢰 가능한 Candidate HVVD fragment가 되도록 만드는 것이다.

### 10.1 Confidence 기준

`confidence`는 LLM의 주관적 확신이 아니라, 제공된 evidence의 완전성과 일관성에 기반한 후보 분류 신뢰도이다.

```
HIGH:
  source, sink, data-flow, missing check evidence가 모두 명확하고,
  evidence_id로 추적 가능하며,
  label 선택에 필요한 주요 근거가 충분한 경우.

MEDIUM:
  source-to-sink flow는 있으나 일부 check, wrapper, source trust,
  call chain, guard 여부 근거가 불완전한 경우.

LOW:
  관련 sink 또는 module context는 있으나
  flow, source trust, guard 판단 근거가 약한 경우.
```

Post-Processor는 LLM이 반환한 confidence가 evidence completeness와 맞지 않으면 조정하거나 flag를 추가할 수 있다.

## 11. GENERIC_CODE_CANDIDATE_HVVD 생성

Post-Processor를 통과한 LLM 출력은 F2-B의 최종 산출인 `GENERIC_CODE_CANDIDATE_HVVD`로 변환된다.

```
GENERIC_CODE_CANDIDATE_HVVD
├─ candidate_id
├─ candidate_type
├─ lifecycle_state
├─ source_stage
├─ target
├─ routing_result
├─ detector_results
├─ primary_root_cause_candidates
├─ evidence_summary
├─ exposure_status
└─ limitation
```

초기 `exposure_status`는 다음과 같이 둔다.

```
exposure_status: NOT_CLASSIFIED
```

이는 F2-B가 외부 입력면 노출 여부를 판단하지 않는다는 점을 명확히 하기 위한 값이다. OCPP 노출성은 F2-C External Exposure Classification에서 다루는 exposure_surface 중 하나로 분류된다.

### 11.1 Multi-detector 결과 병합 정책

하나의 evidence가 복수 Detector로 routing될 수 있으므로, `GENERIC_CODE_CANDIDATE_HVVD` 생성 시 병합 정책이 필요하다.

기본 원칙은 다음과 같다.

```
동일 source-flow-sink evidence를 공유하면
하나의 Candidate HVVD 안에 detector_results로 병합한다.

서로 다른 source-flow-sink 또는 서로 다른 root cause를 가지면
별도 Candidate HVVD로 분리한다.
```

병합 기준은 다음과 같다.

```
하나의 Candidate HVVD로 병합하는 경우:
  - 동일 source 또는 동일 external input을 공유함
  - 동일 call chain 또는 data-flow segment를 공유함
  - 동일 파일/함수/모듈의 동일 취약 후보 맥락에 속함
  - 위험 유형은 다르지만 하나의 exploit narrative로 설명 가능함

별도 Candidate HVVD로 분리하는 경우:
  - source가 다름
  - sink가 완전히 다름
  - root cause가 독립적임
  - remediation strategy가 다름
  - 하나의 후보로 묶으면 evidence 설명이 혼재됨
```

예를 들어 다음 evidence는 하나의 Candidate HVVD로 병합할 수 있다.

```
firmware_url
  → sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url)
  → system(cmd)
  → install_firmware("/tmp/fw.bin")
```

이 경우 detector_results는 다음과 같이 구성될 수 있다.

```

  - COMMAND_INJECTION
  - MEMORY_SAFETY
  - FIRMWARE_OTA
```

Candidate confidence는 Detector별 confidence를 그대로 유지하는 것이 바람직하다. 단일 confidence로 강제 통합하면 Command Injection, Memory Safety, Firmware OTA Weakness의 의미가 왜곡될 수 있으므로, F4 Risk Scoring에서 detector별 confidence와 evidence strength를 별도 factor로 반영한다.

## 12. F2-C External Exposure Classification 연결

F2-C는 F2-B의 `GENERIC_CODE_CANDIDATE_HVVD`가 외부 입력면을 통해 도달 가능한지 분류하는 단계이다.

F2-B는 Command Injection, Memory Safety, Firmware / OTA Weakness, Backend Injection, Unsafe External Resource 등 일반 코드 취약 후보를 생성한다. 그러나 F2-B 단계에서는 해당 후보가 외부 입력 경로에서 도달 가능한지, OCPP handler에서 연결되는지, REST API나 Admin UI에서 호출 가능한지, 또는 내부 함수에 한정되는지 판단하지 않는다.

따라서 F2-C는 취약 유형 분류 단계가 아니라, F2-B generic candidate의 **External Exposure Classification**을 수행하는 계층이다.

```
F2-C. External Exposure Classification
=
F2-B generic 취약 후보가
OCPP, REST API, Admin UI, CLI, OTA Channel, MQTT, Local Config 등
외부 또는 운영 입력면에서 도달 가능한지 분류하는 단계
```

초기 MVP에서는 OCPP action handler 또는 OCPP payload field에서 candidate function/sink까지 도달 가능한지를 우선 판정한다. 그러나 F2-C는 OCPP 전용 단계가 아니다. 향후 Java CSMS, 충전기 관리 서버, 운영 포털, OTA 관리 모듈, 로컬 관리 CLI 등으로 확장될 수 있다.

---

### 12.1 F2-C의 분류 체계

F2-C의 결과는 `exposure_class`와 `exposure_surface`를 분리하여 표현한다.

`exposure_class`는 외부 입력면 도달 가능성의 수준을 나타내고, `exposure_surface`는 어떤 입력면에서 도달 가능한지를 나타낸다.

---

### 12.1.1 exposure_class

F2-C의 기본 `exposure_class`는 다음과 같다.

```
EXTERNAL_EXPOSED:
  후보 function/sink가 외부 입력면 또는 운영 입력면에서 도달 가능한 근거가 존재함

INTERNAL_ONLY:
  후보는 존재하지만 외부 입력면에서 도달 가능한 근거가 없으며,
  내부 함수, 로컬 유틸리티, 테스트 코드, 배치 작업, 내부 관리 로직 등에 한정됨

UNKNOWN_EXPOSURE:
  dynamic dispatch, callback, reflection, function pointer, unresolved framework boundary,
  간접 호출, 불완전한 call graph 등으로 외부 도달성을 판단할 수 없음
```

---

### 12.1.2 exposure_surface

`exposure_surface`는 다음 값 중 하나 이상으로 표현한다.

```
OCPP:
  OCPP action handler 또는 OCPP payload field에서 candidate function/sink까지
  call/data-flow 근거가 존재함

REST_API:
  REST endpoint, HTTP controller, API route 등에서 candidate function/sink까지
  도달 가능한 근거가 존재함

ADMIN_UI:
  관리자 웹 UI 또는 운영 콘솔 입력에서 candidate function/sink까지
  도달 가능한 근거가 존재함

CLI:
  로컬 또는 원격 관리 CLI 입력에서 candidate function/sink까지
  도달 가능한 근거가 존재함

OTA_CHANNEL:
  OTA update, firmware package download/install 경로에서
  candidate function/sink까지 도달 가능한 근거가 존재함

MQTT:
  MQTT topic/message handler에서 candidate function/sink까지
  도달 가능한 근거가 존재함

LOCAL_CONFIG:
  설정 파일, 환경 변수, 로컬 configuration loader에서
  candidate function/sink까지 도달 가능한 근거가 존재함

FILE_IMPORT:
  외부 파일 업로드, 진단 파일 import, 설정 파일 import 경로에서
  candidate function/sink까지 도달 가능한 근거가 존재함

UNKNOWN:
  입력면 유형을 특정할 수 없음
```

초기 MVP에서는 다음 세 가지를 우선 사용한다.

```
EXTERNAL_EXPOSED + OCPP
INTERNAL_ONLY
UNKNOWN_EXPOSURE
```

---

### 12.2 F2-B와 F2-C의 책임 경계

F2-B의 출력인 `GENERIC_CODE_CANDIDATE_HVVD`는 일반 코드 취약 후보이다.

F2-B는 다음을 판단하지 않는다.

```
- OCPP 도달성
- REST API 도달성
- Admin UI 도달성
- CLI 도달성
- OTA channel 도달성
- runtime exploitability
- confirmed vulnerability
```

따라서 F2-B의 초기 exposure 상태는 다음과 같이 둔다.

```
exposure_status: NOT_CLASSIFIED
```

이는 F2-B 결과가 F2-C의 external exposure classification을 기다리는 상태라는 의미이다.

F2-C는 F2-B의 `vulnerability_class`나 `classification_label`을 변경하지 않는다. F2-C는 해당 candidate가 어떤 외부 입력면과 연결되는지에 대한 별도 evidence를 추가한다.

```
F2-B:
  classification_label 생성
  예: COMMAND_INJECTION_LIKELY

F2-C:
  exposure_class / exposure_surface 생성
  예: EXTERNAL_EXPOSED + OCPP
```

중요한 점은 다음과 같다.

```
EXTERNAL_EXPOSED ≠ confirmed vulnerability
EXTERNAL_EXPOSED + OCPP ≠ confirmed remotely exploitable vulnerability
OCPP exposure ≠ runtime exploitability
```

---

### 12.3 예시: OCPP UpdateFirmware 경로에서 도달 가능한 Generic Candidate

예를 들어 F2-B candidate가 다음과 같다고 하자.

```
GENERIC_CODE_CANDIDATE_HVVD:
  function:
    install_firmware_from_url()

  detector:
    COMMAND_INJECTION

  classification_label:
    COMMAND_INJECTION_LIKELY

  flow:
    firmware_url -> sprintf(cmd) -> system(cmd)

  exposure_status:
    NOT_CLASSIFIED
```

F2-C에서 다음 call chain과 field flow를 확인할 수 있다면:

```
handleUpdateFirmware(req)
  → firmwareUpdateService(req.location)
  → install_firmware_from_url(req.location)
  → system(cmd)
```

그리고 field flow가 다음과 같이 연결된다면:

```
UpdateFirmware.location
  → req.location
  → firmware_url
  → sprintf(cmd)
  → system(cmd)
```

F2-C는 이 후보를 다음과 같이 분류한다.

```
exposure_class:
  EXTERNAL_EXPOSED

exposure_surface:
  OCPP
```

### 12.5 Candidate HVVD 유형 보강

F2-C 결과에 따라 candidate type은 다음처럼 보강될 수 있다.

```
GENERIC_CODE_CANDIDATE_HVVD
  ↓
EXTERNAL_EXPOSED_GENERIC_CANDIDATE_HVVD
```

OCPP surface가 확인된 경우에는 하위 유형으로 다음처럼 표현할 수 있다.

```
GENERIC_CODE_CANDIDATE_HVVD
  ↓
EXTERNAL_EXPOSED_GENERIC_CANDIDATE_HVVD
      └─ OCPP_EXPOSED_GENERIC_CANDIDATE_HVVD
```

다만 이 보강은 후보의 외부 노출 근거를 추가하는 것이지, confirmed vulnerability로 승격하는 것이 아니다.

```
OCPP_EXPOSED_GENERIC_CANDIDATE_HVVD
≠ CONFIRMED_HVVD
```

`CONFIRMED_HVVD` 상태 전이는 F5 runtime validation, protocol behavior validation, 재현 evidence, crash/exception/runtime sink evidence 등 별도 runtime evidence가 있을 때만 가능하다.

### 12.6 INTERNAL_ONLY 예시

F2-B가 다음 후보를 생성했다고 가정한다.

```
GENERIC_CODE_CANDIDATE_HVVD:
  function:
    run_internal_maintenance_script()

  detector:
    COMMAND_INJECTION

  classification_label:
    COMMAND_INJECTION_POSSIBLE

  flow:
    internal_constant -> sprintf(cmd) -> system(cmd)
```

F2-C에서 이 함수가 외부 entrypoint, OCPP handler, REST API, Admin UI, CLI, OTA channel과 연결되지 않고 내부 배치 작업 또는 테스트 코드에서만 호출되는 것으로 확인되면 다음처럼 분류한다.

```json
  "classification_target": "GENERIC_CODE_CANDIDATE_HVVD",
  "exposure_class": "INTERNAL_ONLY",
  "exposure_surfaces": [],

    "Function is only called by nightlyMaintenanceJob().",
```

### 12.8 설계 원칙 요약

F2-C External Exposure Classification의 설계 원칙은 다음과 같다.

```
1. F2-C는 F2-B generic candidate의 external exposure를 분류한다.

2. F2-C는 취약 유형 분류기가 아니다.

3. F2-C는 F2-B의 vulnerability_class나 classification_label을 변경하지 않는다.

4. F2-C는 OCPP 전용 단계가 아니다. OCPP는 exposure_surface 중 하나이다.

5. 초기 MVP에서는 OCPP exposure를 우선 다루되, 구조는 REST API, Admin UI, CLI, OTA channel, MQTT, LOCAL_CONFIG, FILE_IMPORT로 확장 가능해야 한다.

6. EXTERNAL_EXPOSED는 confirmed vulnerability가 아니다.

7. EXTERNAL_EXPOSED + OCPP는 confirmed remote exploitability가 아니다.

8. INTERNAL_ONLY는 현재 정적 evidence 기준 외부 entrypoint가 확인되지 않았다는 뜻이다.

9. UNKNOWN_EXPOSURE는 내부 전용이라는 뜻이 아니라, 외부 도달성을 판단할 evidence가 부족하다는 뜻이다.

10. CONFIRMED_HVVD는 F2-C가 아니라 F5 또는 별도 runtime evidence가 있을 때만 가능하다.
```

## 13. 연구적 장단점 및 평가 전략

### 1. 연구적 의의

Type-specific LLM Vulnerability Candidate Classification은 범용 LLM이 소스코드를 자유롭게 해석하여 취약 여부를 단정하는 방식이 아니라, 정적 분석으로 추출된 `Analysis Target Evidence Input`을 취약 유형별 Detector Package가 정의한 label space와 rules에 따라 General-purpose LLM Engine이 분류하는 방식이다.

이 접근의 핵심은 LLM을 최종 취약점 확정기로 사용하는 것이 아니라, 정적 분석 evidence를 해석하고 후보를 구조화하는 `evidence-bounded candidate classifier`로 사용하는 데 있다.

```
Static Evidence
→ Detector Routing
→ Type-specific Detector Package Selection
→ LLM_REQUEST 구성(Prompt + LLM_CALL_INPUT)
→ General-purpose LLM Engine 호출
→ TYPE_SPECIFIC_DETECTOR_OUTPUT
→ Post-Processor
→ GENERIC_CODE_CANDIDATE_HVVD
```

따라서 이 방식은 전기차 충전 인프라/OCPP 도메인처럼 공개 취약 코드 데이터가 부족하고, 도메인 문맥이 중요하며, 분석 결과의 근거 추적성이 필요한 문제에 적합하다.

---

### 2. 장점

Type-specific LLM Vulnerability Candidate Classification은 순수 ML 모델보다 항상 높은 accuracy를 보장하는 방식은 아니다. 그러나 전기차 충전 인프라/OCPP 도메인처럼 데이터가 부족하고, 코드 문맥과 도메인 의미가 중요하며, 분석 결과의 근거 추적성이 필요한 환경에서는 연구적으로 강한 장점을 가진다.

#### 2.1 학습 데이터 부족 문제에 대한 현실적 대응

순수 ML 기반 취약점 탐지 모델은 충분한 양의 라벨링 데이터가 있어야 성능을 기대할 수 있다. 그러나 전기차 충전 인프라, OCPP handler, firmware update module, diagnostic command wrapper, charging daemon, certificate/key store와 같은 도메인 특화 코드는 공개 데이터가 제한적이다.

Type-specific Detector Package 기반 LLM 후보 분류 방식 은 대규모 학습 데이터 없이도 다음 정보를 기반으로 동작할 수 있다.

```
- source candidate
- sink candidate
- data-flow evidence
- call-chain evidence
- observed checks
- missing / weak check candidates
- detector_specific_rules
- allowed_label_space
```

즉, 학습 데이터가 부족한 초기 연구 단계에서도 PoC 구현과 실험이 가능하다.

---

#### 2.2 도메인 지식 반영이 용이함

전기차 충전 인프라 취약점은 일반 CWE 패턴만으로 충분히 설명되지 않는 경우가 많다. 예를 들어 `UpdateFirmware.location`은 단순 문자열 입력이 아니라 firmware download URL이라는 도메인 의미를 가진다.

Type-specific Detector Package 기반 LLM 후보 분류 방식은 F1 OCPP-centric Knowledge Layer, generic security seed, detector_specific_rules를 통해 도메인 지식을 명시적으로 주입할 수 있다.

예를 들어 Firmware / OTA Weakness Detector에서는 다음과 같은 도메인 기준을 직접 반영할 수 있다.

```
- firmware URL 검증 여부
- trusted host 강제 여부
- firmware signature verification 여부
- install block on verification failure 여부
- rollback version check 여부
```

이는 순수 ML 모델이 학습 데이터만으로 자동 획득하기 어려운 도메인 판단 기준이다.

---

#### 2.3 설명 가능성과 근거 추적성이 높음

ML 모델은 높은 분류 성능을 보일 수 있지만, 왜 특정 코드를 취약 후보로 판단했는지 설명하기 어렵다. 

반면 Type-specific Detector Package 기반 LLM 후보 분류는 출력 schema에 다음 항목을 강제한다.

```
- classification_label
- source_summary
- sink_summary
- flow_summary
- observed_checks
- missing_or_weak_checks
- root_cause_candidate
- related_cwe
- evidence_basis
- confidence
- limitation
```

따라서 분석 결과는 단순히 “취약함”이 아니라 다음 형태로 설명된다.

```
firmware_url이 external input으로 식별되었고,
sprintf를 통해 command string에 삽입되었으며,
system()으로 전달되는 source-to-sink flow가 관찰되었다.
그러나 shell-free execution, argument allowlist, metacharacter neutralization 근거는 관찰되지 않았다.
```

이는 연구 결과의 재현성, 검토 가능성, 실무 적용성을 높인다.

---

#### 2.4 LLM 환각 억제 구조를 가짐

Raw-code LLM 분석은 LLM이 코드에 없는 흐름을 추론하거나, runtime exploitability를 단정하거나, OCPP 원격 공격 가능성을 과잉 주장할 위험이 있다.

본 방식은 이를 줄이기 위해 다음 장치를 둔다.

```
- Prompt의 evidence-only rule
- Detector Control Input의 evidence_usage_policy
- allowed_label_space
- allowed_cwe_set
- forbidden_claims
- required_output_schema
- Post-Processor의 evidence consistency check
```

따라서 LLM은 자유 서술자가 아니라 제한된 후보 분류기로 동작한다.

---

#### 2.5 취약 유형별 판단 기준을 분리할 수 있음

Command Injection, Memory Safety, Firmware / OTA Weakness는 서로 다른 판단 기준을 가진다. 하나의 범용 모델로 이를 모두 처리하면 label과 근거가 혼재될 수 있다.

Type-specific Detector Package 방식은 취약 유형별로 다음을 분리한다.

```
- detector_type
- allowed_label_space
- allowed_cwe_set
- detector_specific_rules
- missing_or_weak_check_candidates
```

예를 들어 Command Injection Detector는 command string과 shell execution sink를 중심으로 판단하고, Memory Safety Detector는 fixed-size buffer, copy size, bounds check를 중심으로 판단한다. 이 구조는 분석 기준을 명확하게 만들고, 평가 실험도 취약 유형별로 분리할 수 있게 한다.

---

#### 2.6 후처리 기반 품질 통제가 가능함

LLM 출력은 바로 Candidate HVVD가 되지 않는다. Post-Processor가 다음을 검증한다.

```
- JSON schema 준수 여부
- classification_label이 allowed_label_space 안에 있는지
- related_cwe가 allowed_cwe_set 안에 있는지
- evidence_basis가 입력 evidence를 참조하는지
- forbidden claim 포함 여부
- confidence / limitation 누락 여부
```

이로 인해 LLM 출력의 불안정성을 시스템적으로 흡수할 수 있다. 이는 연구 실험에서 `Label Validity Rate`, `Evidence Consistency Rate`, `Forbidden Claim Rate` 같은 지표로 측정할 수 있다.

---

### 3. 단점 및 한계

#### 3.1 정적 분석 evidence 품질에 강하게 의존함

이 방식의 핵심 입력은 `Analysis Target Evidence Input`이다. 따라서 정적 분석이 source, sink, data-flow, observed check를 잘못 추출하면 LLM 판단도 잘못될 수 있다.

예를 들어 실제로는 sanitizer가 존재하지만 정적 분석이 이를 `observed_checks`에 포함하지 못하면, LLM은 `LIKELY`로 과잉 판단할 수 있다. 반대로 source-to-sink flow가 누락되면 실제 위험 후보를 `NO_EVIDENCE` 또는 `UNKNOWN`으로 분류할 수 있다.

즉, 이 방식의 성능은 LLM 자체보다 다음 요소에 크게 좌우된다.

```
- source 식별 정확도
- sink 식별 정확도
- interprocedural data-flow 정확도
- wrapper/helper 함수 해석 정확도
- observed check 탐지 정확도
- missing check 후보 생성 품질
```

---

#### 3.2 Prompt와 규칙 설계에 따른 편향 가능성

`detector_specific_rules`는 LLM이 evidence를 label로 매핑하는 기준이다. 이 규칙이 너무 공격적으로 설계되면 false positive가 증가하고, 너무 보수적으로 설계되면 false negative가 증가한다.

예를 들어 Command Injection Detector에서 `system()` 호출만으로 `LIKELY`를 주도록 설계하면 오탐이 증가한다. 반대로 완전한 source-to-sink flow가 없으면 모두 `UNKNOWN`으로 처리하면 탐지 민감도가 낮아진다.

따라서 detector_specific_rules는 실험을 통해 조정되어야 하며, 규칙 자체가 연구 변수로 관리되어야 한다.

---

#### 3.3 LLM 출력의 비결정성

schema와 label space로 출력 형식을 제한하더라도, LLM은 동일 evidence에 대해 confidence나 limitation 표현을 다르게 생성할 수 있다. 모델 버전, temperature, prompt wording에 따라 결과가 달라질 수 있다.

이를 완화하려면 다음이 필요하다.

```
- temperature 낮게 설정
- JSON schema validation
- deterministic prompt template
- 재호출 정책
- Post-Processor 기반 정규화
- 동일 입력 반복 실험을 통한 안정성 측정
```

연구적으로는 `Output Stability Rate` 또는 `Label Consistency Rate`를 별도 지표로 측정하는 것이 좋다.

---

#### 3.4 최종 취약점 확정 능력은 제한적임

F2-B의 Type-specific Detector Package 기반 LLM 후보 분류는 정적 evidence 기반 후보 분류이므로, 다음을 판단하지 않는다.

```
- runtime exploitability
- 실제 공격 가능성
- OCPP remote reachability
- state-dependent exploitability
- target 환경에서의 실제 동작 여부
```

따라서 `COMMAND_INJECTION_LIKELY`는 “정적 근거상 command injection 후보 가능성이 높다”는 의미이지, 실제 exploit이 가능하다는 의미가 아니다.

이 한계는 F2-C, F3, F4, F5, F6와의 분리된 역할 정의를 통해 보완해야 한다.

---

#### 3.5 ML 모델 대비 대량 처리 비용이 클 수 있음

순수 ML classifier는 학습 이후 추론 비용이 낮고 대량 코드 처리에 유리할 수 있다. 반면 Detector Package 기반 LLM 호출은 호출 비용과 응답 시간이 상대적으로 크다.

특히 다음 경우 비용이 증가한다.

```
- evidence가 많을 때
- 여러 Detector로 multi-routing될 때
- Post-Processor 재호출이 필요할 때
- code slice와 call chain이 길 때
```

따라서 실제 시스템에서는 Detector Routing으로 불필요한 LLM 호출을 줄이고, Rule-only로 충분한 case는 LLM 호출을 생략하는 hybrid optimization이 필요하다.

---

#### 3.6 평가 데이터셋 구축이 여전히 필요함

대규모 학습 데이터는 필요하지 않더라도, 연구적 검증을 위해서는 benchmark dataset이 필요하다. 특히 다음 유형의 샘플이 균형 있게 필요하다.

```
- true positive case
- false positive 유도 case
- guarded case
- partial flow case
- unknown case
- OCPP reachable case
- non-OCPP-exposed case
```

이 데이터셋이 없으면 Type-specific Detector Package 기반 LLM 후보 분류가 실제로 Rule-only 또는 Static Analyzer-only보다 나은지 주장하기 어렵다.

---

### 4. ML 기반 접근과의 비교

연구적으로는 이 방식을 ML 모델의 대체재라기보다, 데이터 부족 도메인에서의 evidence-guided classification 방식으로 보는 것이 적절하다.

| 구분 | 순수 ML 모델 | Type-specific Detector Package 기반 LLM 후보 분류 |
| --- | --- | --- |
| 학습 데이터 요구 | 높음 | 낮음 |
| 도메인 지식 반영 | 학습 데이터에 의존 | Detector rule과 KB로 명시적 반영 가능 |
| 설명 가능성 | 낮거나 별도 XAI 필요 | evidence_basis로 기본 제공 |
| 출력 통제 | 모델 설계에 의존 | label space, schema, post-processing으로 통제 |
| 환각 위험 | 없음 또는 낮음 | 존재하나 guardrail로 완화 |
| 대량 처리 비용 | 낮음 | 상대적으로 높음 |
| 초기 PoC 적합성 | 데이터 부족 시 낮음 | 높음 |
| 장기 확장성 | 데이터 축적 시 높음 | ML ranker와 결합 가능 |

---

### 5. 연구적 포지셔닝

이 방식의 연구적 가치는 “LLM을 이용해 취약점을 직접 찾는다”에 있지 않다. 핵심은 다음에 있다.

```
정적 분석 기반 code evidence를
취약 유형별 Detector Package가 정의한
명시적 label space와 detector_specific_rules에 따라 
General-purpose LLM Engine이 분류하고,
그 결과를 schema validation과 evidence consistency check로 검증하여
Candidate HVVD로 구조화하는 것
```

따라서 본 방식은 다음과 같이 포지셔닝하는 것이 적절하다.

```
A type-specific, evidence-bounded LLM classification framework
for source-code-side vulnerability candidate generation
in OCPP-based EV charging infrastructure.
```

---

### 6. 연구 가설

본 연구에서 검증할 수 있는 가설은 다음과 같다.

```
H1.
Type-specific Detector Package 기반 LLM 후보 분류는
Raw-code General LLM보다 label validity와 evidence consistency가 높다.

H2.
Type-specific Detector Package 기반 LLM 후보 분류는
Rule-only 방식보다 partial flow, weak guard, wrapper/helper context 판단에서 높은 F1-score를 보인다.

H3.
Post-Processor를 결합하면 LLM 출력의 forbidden claim과 schema violation을 유의미하게 줄일 수 있다.

H4.
Detector Routing을 적용하면 모든 Detector를 무차별 호출하는 방식보다
분석 비용을 줄이면서 유사한 recall을 유지할 수 있다.

H5.
External Exposure Classification을 F2-B와 분리하면
LLM의 external reachability 및 OCPP remote exploitability 과잉 단정을 줄일 수 있다.
```

---

### 7. 평가 지표

단순 accuracy만으로는 이 방식의 장점을 충분히 평가하기 어렵다. 다음 지표를 함께 사용해야 한다.

```
탐지 성능:
- Accuracy
- Precision
- Recall
- F1-score
- False Positive Rate
- False Negative Rate

출력 품질:
- Label Validity Rate
- JSON Schema Validity Rate
- CWE Match Rate
- Evidence Consistency Rate
- Limitation Completeness Rate
- Forbidden Claim Rate

도메인 적합성:
- External Exposure Overclaim Rate
- OCPP Overclaim Rate
- Guarded Case Accuracy
- Partial Flow Handling Accuracy
- Detector Routing Accuracy
```

특히 ChargeGuard-HVVD에서는 `Evidence Consistency Rate`, `External Exposure Overclaim Rate`, `Guarded Case Accuracy`가 중요하다.

MVP에서는 `External Exposure Overclaim Rate`의 하위 지표로 `OCPP Overclaim Rate` 를 함께 측정할 수 있다.

---

### 8. 결론

Type-specific LLM Vulnerability Candidate Classification은 순수 ML 모델보다 항상 높은 accuracy를 보장하는 방식은 아니다. 그러나 전기차 충전 인프라/OCPP 도메인처럼 데이터가 부족하고, 코드 문맥과 도메인 의미가 중요하며, 분석 결과의 근거 추적성이 필요한 환경에서는 연구적으로 강한 장점을 가진다.

이 방식의 핵심 장점은 다음과 같다.

```
- 데이터 부족 환경에서 적용 가능
- 도메인 지식 명시적 반영 가능
- evidence 기반 설명 가능
- LLM 환각과 과잉 단정 억제 가능
- Post-Processor를 통한 출력 품질 통제 가능
- Candidate HVVD 생성에 적합
```

반면 한계는 다음과 같다.

```
- 정적 분석 evidence 품질에 의존
- detector_specific_rules 설계 편향 가능
- LLM 출력 비결정성 존재
- 최종 취약점 확정 능력은 제한적
- 대량 처리 비용이 ML보다 클 수 있음
- 평가용 benchmark dataset 구축 필요
```

따라서 본 연구에서는 Type-specific Detector Package 기반 LLM 후보 분류를 최종 취약점 판정 모델이 아니라, 정적 분석 evidence를 기반으로 취약 후보를 일관되게 분류하고 근거와 한계를 구조화하는 Candidate HVVD 생성 모델로 정의하는 것이 가장 적절하다.

# 부록 A. Command Injection Detector Package 중심 Full Example

## A.1 분석 대상 코드

다음 코드는 충전기 펌웨어 업데이트 모듈의 일부라고 가정한다.

```c
// file: firmware_update.c

int install_firmware_from_url(const char *firmware_url) {
    char cmd[512];

    if (firmware_url == NULL) {
        return -1;
    }

    sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url);
    system(cmd);

    return install_firmware("/tmp/fw.bin");
}
```

이 코드는 외부에서 전달된 `firmware_url` 값을 shell command 문자열에 삽입한 뒤 `system()`으로 실행한다. 따라서 F2-B에서는 Command Injection 후보로 분석될 수 있다.

단, 이 시점에서는 해당 함수가 외부 입력면에서 도달 가능한지는 판단하지 않는다. OCPP 입력 경로는 F2-C External Exposure Classification에서 다루는 exposure_surface 중 하나로 별도 분류한다.

## A.3 Detector Routing

정적 분석 evidence를 기반으로 Detector Routing을 수행한다. Detector Routing은 LLM이 수행하는 취약점 판단이 아니라, 정적 분석 evidence, sink taxonomy, module context, security seed를 기반으로 수행되는 rule/static 기반 pre-routing 단계이다. LLM은 routing 이후 선택된 Detector Package가 구성한 LLM_REQUEST를 통한 candidate classification에만 사용된다.

이 예시는 Command Injection Detector 중심으로 설명하지만, 실제 라우팅 관점에서는 동일 evidence가 복수 Detector로 분기될 수 있다. 특히 `char cmd[512]`와 `sprintf()`는 Memory Safety 관점의 후보 signal이 될 수 있고, `install_firmware()` 호출은 Firmware / OTA Weakness 관점의 후보 signal이 될 수 있다.

### A.3.1 Routing Signal

```
Routing Signals:
- sink_api: system
- sink_type: shell_command_execution
- api: sprintf
- buffer_pattern: fixed_size_stack_buffer
- module_context: firmware_update
- data_flow: external_input → command_string → shell_execution
- flow_pattern: firmware_url → download command → local artifact → install
- security_seed: CMD_INJECTION
```

## A.6 Post-Processor 검증

Post-Processor는 LLM 출력을 그대로 신뢰하지 않고 다음 검증을 수행한다.

```
Post-Processor Validation

1. JSON Schema Validator
   - TYPE_SPECIFIC_DETECTOR_OUTPUT schema를 만족하는가?

2. Detector Type Validator
   - detector_type == COMMAND_INJECTION 인가?

3. Label Space Validator
   - classification_label이 allowed_label_space 안에 있는가?
   - COMMAND_INJECTION_LIKELY는 허용 label인가?

4. CWE Set Validator
   - related_cwe가 allowed_cwe_set 안에 있는가?
   - CWE-78은 허용 CWE인가?

5. Evidence Consistency Checker
   - evidence_basis의 evidence_id가 입력 evidence에 존재하는가?
   - SRC-00042, SINK-00042, DFLOW-00042, DFLOW-00043 등이 실제 입력에 있는가?

6. Forbidden Claim Checker
   - confirmed vulnerability, remotely exploitable via OCPP, runtime confirmed 등의 금지 표현이 있는가?

7. Limitation Checker
   - runtime exploitability와 OCPP reachability를 포함한 external exposure를 평가하지 않았다는 limitation이 포함되어 있는가?
```

## A.8 해석

이 예시에서 Command Injection Detector Package에 의해 제어된 General-purpose LLM Engine은 다음 근거로 `COMMAND_INJECTION_LIKELY`를 반환한다.

```
firmware_url
  → sprintf(cmd, "wget %s -O /tmp/fw.bin", firmware_url)
  → system(cmd)
```

판단 근거는 다음이다.

```
- firmware_url은 external_input으로 식별됨
- firmware_url이 command string에 직접 삽입됨
- command string이 system()으로 전달됨
- 관찰된 check는 NULL_CHECK뿐임
- shell-free execution, argument allowlist, shell metacharacter escaping 근거가 없음
```

그러나 이 결과는 다음을 의미하지 않는다.

```
- 취약점 확정 아님
- runtime exploitability 확인 아님
- OCPP remote exploitability 확인 아님
- F5 validation 결과 아님
- CONFIRMED_HVVD 상태 전이 아님
```

따라서 이 결과의 정확한 의미는 다음과 같다.

```
F2-B는 정적 분석 evidence에 근거하여
install_firmware_from_url() 함수에
Command Injection 가능성이 높은 Generic Code Candidate HVVD를 생성한다.

동일 evidence는 Memory Safety Detector Package 또는 Firmware / OTA Weakness Detector Package로도 분기될 수 있으며, 동일 source-flow-sink 맥락을 공유하는 경우
하나의 Candidate HVVD 안에 detector_results로 병합할 수 있다.

외부 입력면과 연결되는지 여부는
F2-C External Exposure Classification에서 별도로 판단한다.

이때 OCPP 입력 경로는 exposure_surface 중 하나로 분류된다.
```

F2-B는 LLM을 취약점 확정기로 사용하지 않는다.

F2-B는 Type-specific Detector Package를 통해 일반 LLM을

evidence-bounded candidate classifier로 제어한다.
